当前主线聚焦三件事：

1. 继续收口高频页面的可维护性与体验一致性

## 2.4 数据库优化与账号服务主线（2026-08-01）

### 2.4.1 主线目标

在现有 SQL 数据基础之上，完成从“固定 default 用户 + 浏览器持久化”向“账号身份、服务端会话、数据库用户隔离、可观测数据访问”的过渡。

本主线同时覆盖数据库正确性、性能、可靠性和账号安全。账号服务是数据库多用户化的前置条件，不能只增加登录页面而不改造 Repository 和数据权限边界。

当前基线：

- SQLite 与 MySQL 均已具备基础 schema，当前 relational schema 为 V2。
- 已有独立认证账号、服务端 session 和 Repository 用户隔离；首个账号会绑定原 `default` 数据。
- `LEDGERFLOW_API_TOKEN` 仅用于服务级 API 保护，不等同于用户登录凭证。
- `server/relationalDataRepository.js` 已从认证 session 接收当前账本用户 ID。
- 数据导入目前以逐行写入为主，bootstrap 会一次性读取多张业务表。
- SQLite 金额字段使用 `REAL`，需要与 MySQL `DECIMAL(20, 6)` 的精度策略统一。

### 2.4.2 P0：建立性能与正确性基线

- [x] 构造 1,000、10,000、100,000 条交易的可重复测试数据。
- [ ] 测量 bootstrap、导入、单行写入、事务提交、响应体大小和内存占用。
- [ ] 对交易列表、账户流水、月度统计、债务还款和投资历史执行 SQLite `EXPLAIN QUERY PLAN` 与 MySQL `EXPLAIN`。
- [ ] 记录连接耗时、SQL 耗时、锁等待、回滚次数和失败原因。
- [ ] 在没有基线证据前，不直接批量增加索引或引入 Redis。

验收：形成优化前基准数据，后续每项优化都能与基线对比。

当前记录：`docs/database-performance-baseline.md` 已记录 1,000 / 10,000 / 100,000 条交易的 SQLite
导入、Bootstrap、响应体大小和两条代表性执行计划；完整领域查询和 MySQL 实例基线仍待后续补齐。

### 2.4.3 P0：账号服务与认证基础

- [x] 新增 `auth_sessions`：用户 ID、session token 哈希、过期时间、撤销时间和最近使用时间。

- [x] 优先使用 Argon2id；如避免原生依赖，则使用经过成本校准的 Node `crypto.scrypt`。

- [ ] 登录成功后轮换会话，支持退出登录、会话撤销、过期清理和异常登录限制。

## 3. 页面改动规范流程

后续任何页面类需求，都按下面流程推进。

### 3.1 页面规划前

1. 先明确页面职责
   - 这是“操作页”“分析页”“管理页”还是“承载页”
   - 不允许一个页面同时承担太多互相冲突的角色

2. 先明确入口与落点
   - 路由落在哪
   - 桌面侧边栏是否需要入口
   - 移动端抽屉是否需要入口
   - 是否要和已有页面形成跳转闭环

3. 先明确复用策略
   - 优先复用现有 `model`、现有组件、现有样式域
   - 禁止为临时页面直接复制整段旧页面逻辑

### 3.2 页面实现中

1. 页面层只负责装配，不堆大段业务计算
2. 可抽出的计算放到对应 `model` 文件
3. 新样式优先进入对应页面域样式文件，不再直接堆入 `src/app/styles/global.css`
4. 页面上的每个主要结论或提示，都要能说明来源，避免“像 AI 编的”
5. 页面按钮文案要直接指向动作，不用模糊表达

### 3.3 页面验收前

每次页面改动至少完成以下检查：

- [ ] 桌面端可用
- [ ] 移动端可用
- [ ] 不出现明显横向溢出 / 按钮挤压 / 文案截断
- [ ] 入口、标题、页面内容三者语义一致
- [ ] 至少完成一次 `npm run build`
- [ ] 若改动高风险链路，补最小测试或手动验收记录

### 3.4 页面完成后

1. 更新本文件中的任务状态
2. 将完成事项追加到 `plans/已完成汇总.md`
3. 若页面新增正式入口，需同步检查：
   - 路由表
   - 懒加载导出
   - 桌面导航
   - 移动端导航
   - 文案与帮助说明
