## 「变动后余额」这一列,在列表里根本接不上

这一版 1 个提交。换到**余额变动**这条线,先确认了这块的两件事是好的,
然后在一个更细的地方发现了断裂。

### 先说核对过的、都正常的部分

- 明细由流水推导,不存在「手工调整 + 流水」重复计数:**298 笔交易 → 298 条明细**
- 手工调整账户余额会生成一条 manual-adjustment 记录,**刷新后仍在**(299 = 298 + 1),
  且变动额与前后余额一致
- 净变动与各账户 (余额 − 初始余额) 之和**精确相等**:都是 ¥102,795.74
- 类型筛选逐个核对:收入 12、还款 3、退款 1、预算 0、手动调整 0;无结果时有专门空态

### 发现的问题:两个键不是同一个

「变动后余额」是按**交易日期**一条条推出来的
(`buildTransactionBalanceChangeEntries` 按 `date → updatedAt → id` 升序推演),
但列表排序和天分组用的是 `createdAt`(≈更新时间)。

两个键一旦分叉 —— 改过日期的交易、或后补的倒填交易 —— 相邻两行的余额就接不上。
读起来像「+¥390.55 之后余额反而变少」,而这列本意是让人对账的。

实测(微信钱包,我从没动过的账户):**24 行里有 12 处断裂**:

```
打车 −18.50 → -6,813.71
火锅 −25.07 → -6,795.21     ← 与上一条接得上
公司楼下简餐 −19.16 → -6,706.46   ← 接不上
加油 −63.68 → -6,770.14           ← -6,770.14 本该在上一条的位置
```

### 改法

- `EntryRow` 增加 `chainTime`(取交易日期,手工调整退回 `createdAt`)
  与 `chainUpdatedTime`(取 `updatedAt`)
- 排序改为与推演顺序**严格互逆**:`(chainTime, chainUpdatedTime, id)` 降序,
  这样从上往下读,余额逐行接得上
- 天分组改用同一个 key —— 组头与明细不再各按一套时间

### 验证

- 修复后逐行校验同一账户:微信钱包 24 行、支付宝 27 行,**断裂 0 处**(修复前 12 处)
- 新增 1 条回归测试(交易日期在前、更新在后的「旧账」必须排在下面,
  且两行的变动后余额接得上);**把排序改回 `createdAt` 后该用例失败**
