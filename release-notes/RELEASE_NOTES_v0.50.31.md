## 单条「彻底删除」一按就删,没有确认;账户还带着看不见的后果

这一版 1 个提交。

### 症状

回收站里三条路径的确认行为本应一致,实际不一致:

| 路径 | 之前 |
| --- | --- |
| 移入回收站 | 有确认 ✓ |
| 清空回收站 | 有确认 ✓ |
| **单条「彻底删除」** | **没有任何确认,点一下立即永久删除** ✗ |

而**账户**还有一层用户在回收站里看不到的后果:账户被彻底删除后,引用它的交易会在**下一次同步**
时被服务端丢弃(导入器会静默丢掉引用无法解析的行)。用户在回收站里只看到「1 个账户」,
看不到那 N 笔交易也要跟着没了。

### 改法(不改删除语义、不决定「该不该允许删除」)

- 单条「彻底删除」前加确认,与另外两条路径一致;
- 账户且仍有交易时,确认文案**如实说明后果**:

  > 该账户下的 **2** 笔交易也会随之消失,且无法恢复。确认彻底删除吗?

这句话描述的是**当前行为**。等「彻底删除账户」的语义定下来(拒绝删除 / 重指派),
这个分支和文案要跟着改 —— 代码注释里已写明。

### 验证(浏览器实测,浏览器直接报出了弹窗原文)

造一个「已进回收站的账户 + 两笔仍引用它的交易」的临时用户,点该账户的「彻底删除」:

- 确认框出现了 ✓
- 数量正确(`{{count}}` 插值 = 2)✓
- 接受之后:账户被删,而且**库里那两笔交易确实随之消失** ✓ —— 完整呈现了那个「看不见的后果」,
  也正是这句文案要说的东西

**如实说明**:我本意是验证「取消后不会删除」,但那条 dialog 最终被接受而非取消,
所以**取消路径**只验证到代码层面(`if (!confirmed) return`),没有在浏览器里跑通。

### 一处仍需你拍板

这条修复只解决「用户有没有机会知道」。**要不要允许彻底删除仍有交易的账户**,仍然需要你定:
拒绝删除(方案 C)/ 重指派到某个账户 / 允许但明确告知。三者的文案与行为不同,我不替你选。
