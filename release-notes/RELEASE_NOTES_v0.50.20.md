## 助手说「这个月花了多少钱」时,把退款当成了又花一笔

这一版 1 个提交。

### 症状

助手的汇总工具(`summarize_transactions`)回答支出时,把**退款/冲正当成又花了一笔**。
真实数据(演示账本 2026-11,支出类口径):

| | 金额 |
| --- | --- |
| 修复后 | **¥7,764.37** ← 与页面「支出 ¥7,764.37」逐分一致 |
| 修复前 | **¥8,545.47** ← 正好是财务分析页当初那个错误数字 |

差值 **2 × ¥390.55 = ¥781.10** —— 和 `v0.50.13` 修的「资金动态看板月支出」**完全是同一个 bug**,
只是这次长在助手的回答里。

### 三处口径错误叠在一起

```
const rows = ctx.transactions.filter((row) => row.type === 'expense' || row.type === 'income');
if (row.type === 'income') current.income += row.amount;
else current.expense += row.amount;        ← 退款行 type 也是 expense,于是又加一笔
```

1. 退款/冲正**没有抵减**,而是累加 —— 支出多算 2×退款;
2. 没有排除「不计入余额」的行(待处理 / 已关闭 / 失败)—— 账户余额那边一直是排除它们的,
   于是会出现「助手说花了 X,账户只少了 Y」;
3. 合计另写了一份,没走共享的 `summarizeTransactions`。

### 改法

改用 `filterCountableTransactions` + 共享的 `summarizeTransactions`;分组累加时按
「退款/冲正与原始方向相反」处理(收入退款抵减收入,支出退款抵减支出)。

### 验证

- 新增回归测试:28 + 100 − 40(退款)= **88**,待处理那 30 不计。
  **把修复退回旧写法,用例立刻失败**(`expected 198 to be 88`)
- 真实数据交叉验证:修复后 `7,764.37` / 修复前 `8,545.47`,与页面逐分对齐
- 前端 **1108 项 / 146 文件**、服务端 **42 项**;`tsc` 0、`eslint` 0

### 顺带:留下发现它的清单脚本

新增 `npm run audit:sums`([脚本](scripts/audit-handrolled-sums.mjs)):列出所有对交易金额
做手工求和的地方,并标出「文件里在对交易求和、却没有引用共享汇总」的高发区。

判定收得很紧(必须有 `.amount`,且同行或上下文带 `type` 判断 / `transactions` / `rows`)——
第一版没这层过滤,把持仓、负债、预算、向量范数都算了进去,55 条里大半是噪声。
收紧后 **13 处、7 处可疑**;修完这个 bug 后降到 **9 处**。

剩下 7 处可疑里,`workbenchUtils` 那 3 行属于「预算型交易算不算支出」那个待决问题,本轮不动。

前几轮我按页面逐个翻,命中率已经降到 0(连着三轮的猜测全被否定:工资工具、汇率换算、
