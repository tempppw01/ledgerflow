## 从回收站恢复「生成支出」写出的流水时,续费日没有推回去

这一版 1 个提交。

### 问题:回收站是可逆的,但订阅那一侧只做了「退」没做「回」

`v0.50.18` 让「删掉订阅生成的流水」把续费日**精确退回**上一期(带 `prevRenewalDate` 快照)。
但同一次操作把快照与关联都清掉了 —— 于是用户从回收站**恢复**那笔流水时,订阅什么都不知道:

| 步骤 | renewalDate | 关联 | status |
| --- | --- | --- | --- |
| 生成后 | 2026-12-28 | 有 | — |
| 删除后(按设计退回) | 2026-11-28 | 无 | — |
| **恢复后** | **2026-11-28** ✗ | **无** ✗ | **due-soon** ✗ |

后果两条:

1. 「续费即将到期 / 已逾期」提醒按**错的日期**算;
2. 再点一次「生成支出」会**为同一个周期重复记一笔**(从 11-28 推进到 12-28,而 12 月那笔
   已经在账上了)—— 直接是钱的问题。

### 改法:按「回收站可逆、彻底删除才不可逆」重新分配职责

| 动作 | 行为 |
| --- | --- |
| 移入回收站 | 日期退回,**保留** prev 快照与关联 |
| 从回收站恢复 | 用同一个 `advanceSubscriptionDate` 把日期推回生成后的值(月末夹取结果确定),并清掉快照 |
| 彻底删除 | 到这里才清掉快照与关联 |

### 验证

- 6 项测试通过(含新增的「恢复后回到已生成状态」「彻底删除才清掉」)
- **证伪**:把恢复侧的重放临时去掉 → 新用例立刻失败
  (`expected '2026-11-28' to be '2026-12-28'`);还原后恢复通过
- 前端 **1153 项 / 154 文件**、服务端 **48 项**;`tsc` 0、`eslint` 0、七道闸门全 0

### 这条是怎么被发现的

不是随机扫出来的,是**自审自己的改动**时发现的:上一轮我专门回头审 `useFinanceStore` 的 diff,
注意到 `delete reverted.prevRenewalDate` 这一行"把可逆性所需的信息删掉了",于是用临时探针
跑出上面那张状态表确认,再在下一轮修掉。

四轮自审全部有收获(量词硬编码、effect 缺依赖、三处漏网取整、这处丢钱风险)——
它们抓的都是**我自己留下的**问题,而其中两处是任何现有闸门都抓不到的。
