## 状态与退款的「单一事实来源」

这一版修的 4 个问题都是同一件事:**同一份数据在不同代码路径上被按不同规则解释**。
后果从「卡片点了没反应」到「余额差出两倍金额」不等。

### 1. 全额退款后的原交易被误判成退款(余额 ×2)

`normalizeTransactionSemantic` 在 `adjustmentKind` 缺失时会猜一行是不是退款,依据里包含
`status === 'refunded'` —— 但应用自己在**全额退款后会把原交易标成 `refunded`**,那行本质是支出。
一旦被判成退款,方向反转:初始 1000 + 一笔 100 支出 → 余额本该 **900**,却变成 **1100**。

**触发路径**:导入账单(解析出的行不带 `adjustmentKind`)→ 对它全额退款 → 之后再导入任意账单
或恢复备份 → 规范化时判成退款,余额凭空多出两倍金额。

修法:推断里去掉 `status === 'refunded'`(只保留备注/分类名的「退款/退货/冲正」线索)。
应用自己写的退款行都显式带 `adjustmentKind`,不依赖推断。

### 2. 导入/恢复后已删除的交易留在主列表、同一笔可能重复

| 不变量 | 修前 |
| --- | --- |
| 带 `trashedAt` 的交易不得留在主列表 | 违规:已删除的记录被当正常记录展示,而余额里排除了它 |
| 同一 id 不得同时出现在两个数组 | 违规:列表、导出、统计会算两遍 |

出口统一收口:主列表里带 `trashedAt` 的行移入回收站;同一 id 两边都有时**以回收站为准**
(宁可让用户手动恢复,也不要把已删除的钱加回账本)。

### 3. 「未分类」三处口径不一致

数据里是 `categoryId: ''`,列表筛选用哨兵值 `__empty_category__`,而助手待办卡片比的却是
字符串 `'uncategorized'` —— **那个值从不存在**。于是:

- 待办卡片**永远不提示补分类**(计数恒为 0)
- 卡片链接 `?categoryId=uncategorized` 被列表静默忽略,**点了没反应**
- 列表把这类记录显示成 `-`,而确认弹层承诺「归入未分类」、导出与图表也写「未分类」

三处统一:计数用「`categoryId` 为空」、链接用哨兵值、列表兜底显示「未分类」。

### 4. 状态筛选与余额口径不一致

列表筛「已完成」用的是 `status === filter`,而没有 status 的历史行(导入的 CSV、老备份)在余额里
是**计入**的 —— 于是「余额里有这笔钱,列表筛不到」。把「缺省状态 = 已完成」收口成
`matchesStatusQuickFilter`,并用测试把「计不计入余额」和「能不能被筛到」绑成同一个结论。
