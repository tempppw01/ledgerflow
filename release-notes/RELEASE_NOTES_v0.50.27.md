## 预算向导从写死的 ¥10,000 开始,无视你已登记的月收入

这一版 1 个提交。

### 症状

预算向导问的第一个数是「每月到手收入」—— 而应用**早就知道**这个数:设置里的登记月收入,
还款管理用它算负债率,助手用它做上下文,投资页用它算可投资现金。

但向导固定从写死的 `DEFAULT_BUDGET_ANSWERS` 起步:

```
{ identity: 'employee', monthlyIncome: 10000, monthlyFixedExpense: 3000, savingsRatio: 0.3 }
```

「重新设置」也是重置回 ¥10,000。于是用户明明登记过收入,一路点下去,**整份预算** ——
固定/储蓄/灵活的分配、执行率、健康度 —— 全按 ¥10,000 算。

演示账本正是这个状态:

| | 值 |
| --- | --- |
| 已确认方案里的月收入 | **¥10,000** |
| 登记月收入 | **¥26,000** |
| 方案的三项分配 | 固定 3,000 + 储蓄 2,100 + 灵活 4,900 = 10,000(方案自身自洽,但基数错了) |

### 改法

- 新增 `buildWizardDefaultAnswers(registeredMonthlyIncome)`:有合法的登记收入就用它,
  没有(0 / undefined / NaN / 负数)才退回默认;**只改收入这一项**,其余仍取默认。
- 向导初始值与「重新设置」都用它;**草稿仍然优先**(用户填到一半的值不会被覆盖)。

### 验证

- 新增 4 条回归测试。**把实现退回「恒用默认」→ 第一条立刻失败**
  (`expected 10000 to be 26000`);另有一条专门测「不修改默认答案常量本身」,
  避免 shared 常量被改脏
- 浏览器实测:打开向导第 1 步 →「身份 上班族 · **收入 ¥26,000.00** · 固定 ¥3,000.00 · 储蓄 30%」
  (修复前是 ¥10,000);并确认**已保存的方案没有被这次改动碰到**
- 前端 **1140 项 / 152 文件**、服务端 **45 项**;`tsc` 0、`eslint` 0、六道命令式闸门全 0

### 这一轮的形状

「**应用已经知道的值,某处却用写死的默认值**」—— 与之前修的「同一概念两处实现」是近亲,
但更隐蔽:它不产生两个互相矛盾的数,而是**忽略已有的数据**,所以从界面上看不出来。
