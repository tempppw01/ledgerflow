## 回收站两处漏网:清空不再绕过账户规则,恢复交易不再留下已删分类的引用

两个改动属于同一类:**界面上的承诺在某一条路径上没有兑现**。
一处是「账户还有交易就不能真删」这条规则漏了「清空回收站」这扇门;
另一处是「删分类 → 相关交易归入未分类」这句承诺漏了「恢复交易」这条回程。

### 一、清空回收站曾经是「账户还有交易就不能真删」这条规则的后门

这是仓库自己记录在案的**静默丢交易**链的入口(`server/orphanAccountReferences.test.js`
顶部写着它):删账户(进回收站,交易保留)→ 清空回收站(账户行真删)→ 下一次整份导入时
那笔交易**从库里消失**(`account_id` 是 NOT NULL,悬垂引用表示不出来)。

store 里「逐个彻底删除」早就按方案 (C) 挡住了 —— 漏的是**另一扇门**:
`clearRecycleBin` 原来无条件清空四个数组,被逐个删挡住的东西从这里直接放走。

| 路径                         | 改动前                                               | 改动后                                                                      |
| ---------------------------- | ---------------------------------------------------- | --------------------------------------------------------------------------- |
| 回收站里逐个「彻底删除」账户 | 被挡住并说明原因(`recycleBin.accountDeleteBlocked`)  | 不变(改用共用的判定函数)                                                    |
| 「清空回收站」               | **无条件清空四个数组** —— 被挡住的东西从这里直接放走 | 跳过被引用着的账户,并说明跳过了几个 / 共几笔交易(`recycleBin.clearBlocked`) |

两条路径有一处**刻意的不对称**(写在 `countBlockingTransactions` 上):逐个删除时
「回收站里的交易」也算引用,清空回收站时不算 —— 后者本来就会把回收站里的交易一起删掉,
再拿它们当理由跳过账户只会让用户困惑(点第二次又突然能清了)。

### 二、恢复交易曾把「已删分类」的引用搬回启用列表

删分类时清掉的是**启用列表**里那些交易的引用(`removeCategory` 遍历 `s.transactions`),
回收站里那一份仍指着它;而恢复交易是把回收站那一行**原样**搬回启用列表。于是

> 删交易 → 删分类 → 恢复交易

三步之后,启用列表里出现一笔引用了**不在启用分类里**的 id 的交易 —— 这个 id 既不是 `''`
(未分类的正式表示)、也没有对应分类。同一份数据于是有四种口径:

| 位置                     | 对这笔交易的行为                                                        |
| ------------------------ | ----------------------------------------------------------------------- |
| 流水列表 / 导出          | 查不到就显示「未分类」,看上去没问题                                     |
| 「未分类」筛选项         | 按 `!categoryId` 判断 —— **认不出它**                                   |
| 助手的「待分类交易」计数 | 同样漏掉它                                                              |
| 首页分类占比             | 按 categoryId 分组,它和真正的未分类是**两个 key、两行同名**的「未分类」 |

服务端对认不出的分类有哨兵兜底(`relationalDataRepository` 的 `uncategorizedCategoryId`),
所以丢的是「分类归属」而不是交易本身;界面上那四处矛盾是真的。

现在 `restoreTransaction` 恢复时若原分类不在启用列表(被移入回收站或已彻底删除),
就把 `categoryId` 清成 `''`,并返回 `{ restoredCount, uncategorizedCount }` ——
与 `permanentlyDeleteAccount` / `clearRecycleBin` 同一套「数量交给界面」的做法;
回收站页面有笔数时弹 `recycleBin.restoreUncategorized` 说明。

**为什么不做成「拒绝恢复」**:那会变成死胡同 —— 用户要恢复这笔交易,就得先把那个他刚
决定删掉的分类恢复回来。清成未分类与删除分类时写下的承诺是同一句;恢复顺序只影响结果
(先恢复分类再恢复交易,引用会保留),两种都不留悬垂引用。

### 三、破坏性验证

两条闸门各自被拆开试过(脚本留在 `.audit/`,先跑基线、再破坏、再逐字节还原)。

| 破坏方式                                   | 期望                            | 实测                                                             |
| ------------------------------------------ | ------------------------------- | ---------------------------------------------------------------- |
| `clearRecycleBin` 改回「无条件清空四数组」 | 规则用例与页面用例都变红        | **4 failed / 2 passed** → exit 1;还原后逐字节一致、6 条全过      |
| 清空回收站页面去掉那句说明                 | 页面用例变红                    | **1 failed / 5 passed** → exit 1                                 |
| 去掉「恢复时清掉失效分类引用」那段规范化   | store 用例与页面用例都变红      | store **3 failed / 4 passed**、页面 **1 failed / 3 passed**      |
| 只去掉页面上的说明                         | 页面用例变红,store 用例不受影响 | 页面 **1 failed / 3 passed**,而 store **7 条全过**(两层各管一段) |
| 还原                                       | 两边逐字节一致、再测全绿        | `restored identical: True`,基线 **11 条全过**                    |

这一版没有在界面上重放那四步(删交易 → 删分类 → 恢复交易):它要往演示账本里真的写数据,
而 `audit:demo-baseline` 正守着那份演示数据。行为由 store 与页面两层用例 + 上面的破坏性验证钉住。

### 五、这一版查证过、没有改的事

- **dev server 里 `/cdn/ui/*.svg` 一批 500 是上游瞬时抖动,不是代码问题**:同一个 URL 立刻
  `curl` 是 **200**、内容正常,重载页面后 **0 报错**。侧栏图标本来就有「取不到就退回字形」的兜底。
- **prettier 红名单的数字会漂**:同一台机器上先后量到 349 / 341 / **358** 个文件,所以它只说明
  「很大一批」,不要当清单用(新写的文件都单独跑过 `prettier --write`,没有增加红名单)。
- **「保留交易」这件事在库里仍然表示不出来**:数据模型那一层**待决策**(四个备选方案写在
  `server/orphanAccountReferences.test.js` 顶部);这一版做的是把界面上的两条路径都堵住,
  服务端「引用不到的行走丢」的既有行为没变,仍由那个测试文件钉住。
