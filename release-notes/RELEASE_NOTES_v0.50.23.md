## 助手导入账单:分类说不清时,被悄悄归到「碰巧排第一」的分类上

这一版 1 个提交。

### 症状

助手解析账单时,如果分类名匹配不上,兜底逻辑会把账单归到**碰巧排第一的那个分类**:

```
resolveCategoryId: 没给名字 / 匹配不上 → categories[0]?.id || 'cat-unknown'
ensureCategoryId:  新建分类失败        → categories[0]?.id || 'cat-unknown'
```

`categories[0]?.id` 这条更隐蔽 —— **账单上会显示一个真分类**,但那不是它该归的类。
分类统计、预算执行数会就此悄悄偏掉,而用户完全看不出来(账单上明明写着「餐饮」)。

`'cat-unknown'` 那条则是不存在的 id(服务端会兜到「未分类」哨兵,所以不丢数据,
但客户端在下次整份导入前一直拿着一个假 id)。

这与 `v0.50.14` 修的 `'acc-unknown'` 是同一形状 —— 那次造出的账户 id 会让交易
「不在任何账户余额里、却计入支出统计」。

### 改法

解析不出来就返回**空串**。应用本来就为「没有分类」准备了「未分类」:列表按未分类显示,
服务端也有每用户的哨兵分类兜底(见 `relationalDataRepository` 的 `uncategorizedCategoryId`)。

### 验证

- 新增 6 条回归测试。把两处兜底改回旧写法,**4 条立刻失败**:
  ```
  匹配不上  → expected 'cat-food' to be ''      ← 悄悄归到第一个分类
  没给名字  → expected 'cat-food' to be ''
  没有分类  → expected 'cat-unknown' to be ''   ← 造出不存在的 id
  新建失败  → expected 'cat-food' to be ''
  ```

### 写测试时踩到自己一个坑

第一版用例我拿「餐饮外卖」当「新建失败」的样本,结果它没失败 —— 因为「餐饮外卖」会
**松散匹配**到「餐饮」(`ensureCategoryId` 的近似匹配是刻意的),根本走不到新建那一步。
换成不重叠的「宠物粮」才真正测到目标分支。

这类「测试没测到我以为的分支」比写错代码更值得记:绿色只能证明我写的断言通过了,
不能证明我测到了想测的地方。
