## 发给模型的账本合计,把退款又算成了一笔支出

这一版 1 个提交。

### 症状

`buildTransactionPromptContext` —— **发给 AI 的那份账本上下文** —— 自己手写了一套聚合:

```ts
if (item.type === 'expense' || item.type === 'repayment') acc.expense += item.amount;
```

而**退款行的 `type` 也是 `expense`**,于是退款被当成「又花了一笔」加了进去,而不是冲减;
待支付/已关闭/失败的行也照样计入。

这正是 v0.50.20 在 `assistantAgentTools` 里修过的**同一个 bug**,只是发生在**上下文构建**这一侧 ——
也就是说 AI 一边被工具纠正,一边从上下文里拿到虚高的支出。

演示账本里有一笔 ¥390.55 的退款,所以模型看到的「支出」比实际多 **¥390.55**。

### 改法(只修这两点,不动支出口径)

- 合计改为按 id 回查原始交易:用共享的 `filterCountableTransactions` 排除不计入的行、
  用共享的 `isTransactionRefundLike` 给退款/冲正取负号;
- **预算型交易仍按原样不计入** —— 支出口径是另一个待决问题,不在这轮范围;
- 送给模型的**行列表不变**(模型仍看得到那些行),只有 `summary` 的算法被修正。

### 验证

- 新增测试:100 支出 + 40 退款 + 30 待支付 → `summary.totalExpense` 必须是 **60**
- **证伪**:把冲减临时去掉 → 同一测试报 `expected 140 to be 60`;还原后 36 项全过
- `audit:sums` 里 `workbenchUtils` 已从告警清单消失(告警文件 3 → 2)
- 前端 **1159 项 / 155 文件**、服务端 **48 项**;`tsc` 0、`eslint` 0、七道闸门全 0

### 顺带判掉清单里另外两处告警(不是 bug)

- `budgetPlan` 的两处求和是**预算分配行**、不是交易行;
- `analysis.ts` 已在用共享汇总,告警是脚本判断较粗。

### 这条是怎么发现的

沿「**找出被绕过的共享助手**」这条线:`audit:sums` 会列出「在求和却没引用共享汇总」的位置。
这条线最近三轮的命中是:支出口径第三份副本 → UTC 日比较 → **这一处**。
