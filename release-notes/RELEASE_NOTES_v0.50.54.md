## 修:备注里带换行的账单,整笔交易会**静默消失**

### 怎么发现的

继续用"造真实形状的输入去撞"的办法。这轮撞的是 CSV 的几个脏情况:

| 情况 | 结果 |
| --- | --- |
| CRLF 换行(Windows 上 Excel 另存就是这样) | 通过(备注也不残留 `\r`) |
| 引号字段里**带逗号**(商家名里很常见) | 通过 |
| 引号字段里**带换行**(备注/商品里真有) | **整行消失,解析出 0 条** |

### 根因

取行是直接 `text.split('\n')`。而 CSV 里**引号内的换行是合法内容**:

```
…, 商户消费, 稻家乐, "招牌菜
第二行", 支出, 39.70, …
```

这一 split 就把一条记录劈成两半,两半都解析不出 —— **整笔交易没了**,而界面上只是"少了一条",
用户根本不会发现少了一笔钱。

### 改动

新增 `splitCsvLines()`:按 `\n` 切行,但**跳过引号内的换行**,并正确处理 `""` 转义。
`parseBillCsvLines` 改用它。

### 验证

新增 `billImport.csvVariants.test.ts`(3 条):CRLF、引号内逗号、引号内换行。

**第三条在修复前就是失败的**(`解析条数: 0`),修完后 3/3 通过 —— 它本身就是这次修复的证据。

前端 1257 项 / 169 文件、服务端全过、十一个闸门 + 演示库基线全 0。

### 连续两轮的共同点

上一轮抓到的是**日期序列号的 `t="n"` 变体**,这一轮是**引号内换行**。两个都不是"没写功能",
而是**边界情况没覆盖** —— 而它们的后果都一样:**交易静默丢失或整份导不进来**。
所以这两轮的产出不是修 bug,而是**把"脏输入"变成仓库里的固定测试**。
