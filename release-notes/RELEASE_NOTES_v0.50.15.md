## 助手里的金额取整,和全项目不是同一套算法

这一版 1 个提交(外加闸门的一条新规则)。

### 症状

金额取整在全项目只有一套真源:`src/shared/lib/money.ts` 的 `roundMoney` —— 它带 EPSILON
修正,并把 `-0` 归一;`roundCurrency` 也是委托给它。文件注释写着:

> 统一走 shared/lib/money:全项目只保留一套取整算法,避免 1.005 在不同模块得到
> 1.00 / 1.01 两种结果。

但助手的两个文件又各自定义了一个**同名**函数:

```
src/features/assistant/agent/creditAgentTools.ts:385
src/features/assistant/agent/investmentAgentTools.ts:136
  function roundMoney(value: number): number { return Number(value.toFixed(2)); }
```

名字一样、算法不同。实测两套在这些值上给出不同结果:

| 值 | 真源 | 助手本地 |
| --- | --- | --- |
| 1.005 | 1.01 | **1**(`toFixed` 连两位小数都不补) |
| 2.675 | 2.68 | **2.67** |
| 0.615 | 0.62 | **0.61** |
| -1.005 | -1.01 | **-1** |
| 16.235 | 16.24 | **16.23** |

影响的是**助手写负债 / 持仓时的金额**:同一个数经助手进来与经界面进来可能差一分钱 ——
正是这份共享实现当初想避免的情况。OCR 出来的单价常带三位小数(2.675 这种),并不罕见。

### 改法

删掉两处本地定义,改为 import 共享的 `roundMoney`。全仓现在 17 处导入、0 处离群。

### 验证

- **新增第三条闸门规则**:不许在别处重新定义 `roundMoney` / `roundCurrency`
  (定义级检查,与另外两条谓词规则同一机制)。**故意加回一份本地 `roundMoney`
  → 闸门报 1 处并给出行号,还原后回到 0**
- `file:line` 级豁免只加了 1 条:`useFinanceStore` 的 `roundCurrency` 是交给 `roundMoney`
  的薄别名(历史调用点多),算法没有第二份
- 前端 **1095 项 / 142 文件**、服务端 **38 项**
- `tsc` 0、`eslint --max-warnings=0` 0、i18n 两闸门 0、`check:dates` 0、`check:money` 0、
  `check:shared-predicates` 0、`audit:ledger-math` 通过

### 仍然需要你拍板(第三次提出)

`isExpenseLike`(支出 + 预算 + 还款)与首页的 `isActualExpenseType`(支出 + 还款)对
**「预算」型交易**判断相反:记一笔 ¥100 的预算型交易后,页头「本月结余」减 100,
而「钱都去哪了」各分类合计不变。这也是**清单里唯一没收敛掉的一项** ——
类型集合的多份副本正卡在这个决策上。选哪边我一行就能改完;或者确认这个类型没用途、
从下拉里去掉,同样一行。
