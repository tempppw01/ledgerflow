## 不再让「旧窗口的快照」覆盖掉别处已经保存的数据

这一版是第二个——也是**最后一个**——需要改行为的决定。至此三件待决事项里,两件落定、一件(纯定义)只剩一个字。

### 之前会发生什么(已严格复现过)

客户端把**整份快照**上传,服务端先删光该用户的行、再按快照重插;而客户端上传前不重新拉取、也不比版本。
于是两个窗口(或手机+电脑)都加载完之后:

- A 记一笔 → 保存成功;
- B 记一笔 → **A 那笔被删掉**,而且**没有任何报错**。

### 现在的行为

- 客户端把「它加载时看到的版本」随每次上传带上(`X-Ledger-Base-Revision`),上传成功后续期;
- 服务端发现版本已变 → **409**,拒绝这次上传,并给出:
  「账本已被另一个窗口或设备改动,已暂停上传,以免把那些改动覆盖掉。请刷新页面后再继续。」
- 客户端识别这条(在 id 冲突判断之前判,因为那条规则含 409 会吞掉它)→ 暂停上传 + 离开保护继续挂着。

### 验证(浏览器端到端 + 数据库核对)

用同一个账号开两个标签页,都先加载完:

| 步骤 | 结果 |
| --- | --- |
| A 记 ¥111 | 保存成功 |
| B(旧版本)记 ¥222 | **被拒绝**,界面给出上面那句话 |
| B 刷新后记 ¥333 | **保存成功** —— 不卡死 |
| **服务端最终数据** | **`[111, 333]`** —— A 那笔完好,222 没覆盖任何东西,333 正常落库 |

补充一条实测:**刷新时浏览器的「有未保存改动」确认框会弹出来**(上一版加的离开保护)—— 也就是说
用户不会在不知情的情况下丢掉那笔被挡下的记录,这是「代价可控」的关键一环。

自动化层面:2 条服务端 HTTP 测试(旧版本 → 409 且库里无写入;当前版本 / 不带头部 → 200),
**证伪过**(去掉校验后第一条失败,期望 409 实得 200)。

### 兼容与可逆

- **不带头部的调用方保持原行为** —— 这是可选的防护,不是强制协议(旧客户端、脚本、测试都不受影响);
- 前端 1167 项 / 157 文件、服务端 48 项全过,九道闸门全 0;
- 不想要:**一行 revert**(分支 `proposal/reject-stale-snapshot-push` 仍在)。
