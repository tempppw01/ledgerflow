## 服务端丢记录时不再静默

这一版 1 个提交。

### 问题

`/api/data/import` 会**静默丢弃**引用无法解析的行(最典型:交易引用的账户已被**彻底删除**),
接口照样回 200,而客户端**从来不读返回里的 `counts`** —— 于是用户丢记录时既没有报错、也没有提示,
只有下次载入才发现少了东西。更糟的是那笔记录只活在内存里,关掉页面就永远没了。

### 改法(只加「检测 + 报告 + 保护」,不改写入行为、不决定产品语义)

| 改动 | 说明 |
| --- | --- |
| `model/syncCountMismatch.ts`(新) | 比对 7 张内容表的「发出行数 vs 服务端存下行数」;已核对客户端 payload 与这 7 张表是 1:1 映射 |
| gate 的推送成功分支 | 有缺口就提示「同步完成,但以下记录没能写入服务端:**交易 1 条**。它们目前只存在当前页面里,请先导出备份再离开。」 |
| 与离开保护保持一致 | 有缺口时**不解除**「离开页面确认」—— 那些记录确实还只活在内存里,此时解除保护等于放用户直接丢掉它们 |
| i18n | zh / en 各加 `dataSync.syncDroppedRecords` |

**失败时倾向不报警**:`counts` 缺失或不是数字时一律当作「不知道」—— 宁可漏报,也不要让所有人
每次同步都看到一条假警告。

### 验证:哪些做到了、哪些没做到

**做到了**
- 7 项单元测试(一致不报 / 少一笔就报 / 同时少两组都报 / 存多了不报 / counts 不可信时不报 /
  payload 形状不对不炸 / 文案量词)
- **实测看到通知真的弹出**:造出悬垂引用后推送,界面出现该通知
- **实测复现服务端丢行**:推送前库里那笔还在,推送后只剩新记的那笔
- **实测离开保护仍然生效**:有未写入记录时刷新,浏览器确认框确实弹出

**没做到(如实记录)**
- 第一次跑时我把插值写成了 `{detail}`(应用约定是 `{{detail}}`),界面上显示出字面量 —— 已修,
  并改用与两个**已在工作**的键相同的约定
- **没有**用 UI 走通完整路径:元素选择器找不到「管理 → 删除」那个控件,试了两轮后放弃。
  所以插值后的最终文案我没在浏览器里再看到一次,只有上面的机制性证据

### 验证中顺带发现的两个事实

1. **客户端的读取路径也会过滤引用无法解析的行** —— 所以「先删账户再刷新」不会触发丢行,
   必须是**客户端已经持有那笔记录**时账户才消失(这正是真实操作顺序);
2. **账户以客户端状态为准**:在库层面删掉账户后,客户端下一次推送又把它写回来了(整份快照语义),
   所以这个场景必须由客户端先删账户。

### 一处根因补充

SQLite 的**外键不允许**删除仍被交易引用的账户 —— 所以「彻底删除账户」的丢数据不是外键失守,
而是导入器的引用校验主动丢行。这条记进根因里,和 `account_id NOT NULL` 并列。
