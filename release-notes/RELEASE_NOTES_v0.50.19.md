## 信用草稿的金额不取整,会带着三位小数落库

这一版 1 个提交。

### 真缺口:解析器在「没有单位」这条分支上完全不取整

`creditDrafts.extractAmount`(把 OCR / 用户输入的金额解析成负债金额)在数字后面**没有单位**时:

```
if (unit.multiplier === 1) { return base; }   ← 直接返回,完全不取整
```

于是「信用卡欠款 **2675.675** 元」会被原样解析成 `2675.675`,带着三位小数一路进草稿。
带单位(「1.5 万」「2 千」)的分支都是取过整的 —— 漏掉的恰恰是**最常见的那条**。

这个是新增测试当场抓到的,不是我读代码看出来的:
写测试时我本来只是想钉住「草稿金额与全项目同一套取整」,结果它报了
`expected 2675.675 to be 2675.68`。

### 顺带:17 处金额取整收敛到共享算法

`money.ts` 写着「全项目只保留一套取整算法,避免 1.005 在不同模块得到 1.00 / 1.01」,
但仍有一批金额走 `Number(x.toFixed(2))` —— 另一套算法(两者的差异:
`2.675` → `2.67` vs `2.68`;`1.005` → `1.00` vs `1.01`)。按「结果是不是账上的金额」筛出并收敛:

| 位置 | 内容 |
| --- | --- |
| `creditDrafts`(3) | 草稿金额解析(含上面那条漏取整的分支) |
| `useAppPreferences`(3) | 负债/还款/持仓的金额归一化 |
| `AssistantPage`(1) | 助手登记的还款后余额 |
| `RepaymentManagementPage`(2) | 还款后的剩余本金 |
| `TransactionsPage`(1) | 剩余可退额度 |
| `InvestmentsPage`(3) | 持仓市值与当日盈亏 |
| `workbenchUtils`(4) | 助手写入负债/还款的金额 |

**刻意没动**:比例/份额类(`toFixed(1)` / `toFixed(4)`,如持仓占比、年化利率)、
给模型的提示文本里的数字、纯展示格式化 —— 它们不是「账上的金额」;
`holdingsShares` 是份额不是金额,同样不动。

### 我自己的清点是错的,已修正

上一版清点时我用的正则是 `Number\([^()]*toFixed\(2\)\)` —— **带嵌套括号的写法全漏了**
(如 `Number((a + b).toFixed(2))`)。实际命中 **63 处**而不是当时以为的 36 处。
这一版换成宽松模式重扫、按用途分类,否则「已经清完」会是个假结论。

### 仍然需要你拍板(第七次提出)

`isExpenseLike`(支出 + 预算 + 还款)与首页的 `isActualExpenseType`(支出 + 还款)对
**「预算」型交易**判断相反:记一笔 ¥100 的预算型交易后,页头「本月结余」减 100,
而「钱都去哪了」各分类合计不变。这是口径清单里唯一没收敛掉的一项。
