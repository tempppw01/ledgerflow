## 分类终于能「两级」用了 —— 点开、原地加,而且真的存下来了

这一版 2 个提交:把二级分类做成真正可用的功能,并在此过程中修掉两个
**数据存不下来**的缺陷。

### 1. 一级分类一律可点开,并在原地新增子分类

原来只有「已有子分类」的分类才是可点的折叠控件 —— 想给「餐饮」挂一个子分类,
只能跑回页面顶部的表单再滚回来,而那一行本身既不可点、也看不出能往下挂东西。

- 一级分类现在**总是**折叠控件(带箭头)
- 有子分类的默认展开;**没有子分类的默认收起**,点开后才给一行
  「还没有子分类,点右侧「+子分类」添加」的交代
  (若沿用默认展开,17 个空分类会同时显示这句提示 —— 那是噪音,不是引导)
- 点「+子分类」直接在**该分类下方**展开输入框:自动聚焦、回车即建、
  建完保持打开以便连续添加,Esc / 取消收起;输入框与子分类同样缩进,视觉上归属父级
- 顶部表单与行内表单共用同一套创建逻辑,校验与图标推断不再两处各写一份

### 2. 子分类从未被持久化(刷新就变一级分类)

端到端验证时发现:新建的子分类**一刷新就变回一级分类**,换设备同样丢。两层根因:

**① 服务端根本没有 `parent_id` 列。** 「子分类」此前只活在浏览器 store 里,
`relationalDataRepository.js` 的插入与读取都没有这个字段。

**② 补上列之后仍然丢。** `ledgerIdScope.js` 的 `ID_KEYS` 漏了 `parentId`:
分类 id 会被加用户作用域前缀,而 parentId 不会,于是「父级是否属于本账本」的校验
永远为假,写入时被落成 `null`。

修法:

- `relationalDatabase.js`:建表加 `parent_id`;**schema v6 → v7**,用 `ADD COLUMN`
  给已有库补列(只加列、不动既有约束,风险最低;本地库已验证自动迁移成功)
- `relationalDataRepository.js`:写入时校验父级确实存在于本次 payload(不留悬空引用),
  读取时映射回 `parentId`
- `ledgerIdScope.js`:`ID_KEYS` 增加 `parentId`

### 3. 删除分类从来存不进去(上一个提交已修,本版一并包含)

删除一个有交易引用的分类,界面显示成功、刷新后分类又回来,同步横幅无限重试。

根因是前后端契约不一致:前端的不变式是**交易的 `categoryId === ''` 即「未分类」**,
而服务端 `category_id` 是 `NOT NULL` + 外键,空串两样都不满足 —— 导入时这些交易被
整行跳过,余额记录却仍引用它们,外键失败让**整个导入回滚**。

改为用一个用户范围内的哨兵分类(`uncategorized:<userId>`)承接:写入时落到它名下,
读取时再映射回 `''`。不动 schema、前端口径与既有测试原样成立。实测:81 笔交易一笔没丢,
悬空引用 0,`PRAGMA foreign_key_check` 无违规。

### 验证

浏览器端到端(真实点击,非模拟):

- 点「餐饮」(0 子分类)可展开并显示提示;其余一级分类显示可点箭头
- 点「+子分类」→ 输入框出现在餐饮下方、自动聚焦 → 输入「MCP午餐」→ 回车即建
- **刷新后仍是餐饮的子分类**(未被提升为一级),餐饮显示「1 个子分类」,无同步错误
- 数据库核对:`MCP午餐.parent_id = 7e522500-cat-food`
- 删除分类后:分类进回收站、81 笔交易归入「未分类」、交易总数不变、无悬空引用
