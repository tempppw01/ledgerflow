## 修:「上传微信账单失败」——xlsx 里的日期是 Excel 序列号

用你发来的真实账单复现了,而且是**两个独立的缺陷**叠在一起。

### 缺陷一:整份文件解析出 0 条(这就是「失败」的原因)

账单的 xlsx 里,**「交易时间」列存的是 Excel 日期序列号**,不是文本:

```
46350.78209490741   商户消费   稻家乐社区厨房   支出   39.7   零钱   支付成功   ...
```

我们的 xlsx 解码器是手写的(解 zip + 读 sharedStrings + 读行 XML),**忽略了单元格样式**,
而"这列是日期"这个信息恰恰在样式里(`xl/styles.xml`)。于是日期列原样变成一串数字,下游
按日期解析**每一行都失败** → **0 条**。

修复:解析 `styles.xml` 找出哪些样式是日期格式,再按 Excel 的 1899-12-30 基准把序列号还原成
`YYYY-MM-DD HH:mm:ss`。**纯算术、不经时区** —— 账单里的时间就是本地墙钟,过一遍 Date 的
时区换算反而会偏移。

### 缺陷二:中性交易被算进了收支(这是「数据不准」的原因)

修好日期之后能解析出 445 条,但合计对不上:

| 项 | 修复前 | 账单自报 |
| --- | --- | --- |
| 收入 | 55088.29 ✗ | **29402.99** |
| 支出 | 11882.08 ✗ | **14522.08** |

原因:微信账单里「收/支」列是 **`/`** 的那 93 笔(**中性交易** —— 转账、零钱提现、理财通转入转出),
既不是收入也不是支出。收/支读不出方向时,代码会落到关键词兜底,于是它们被摊到了收支两边。

修复:收/支明确是 `/` 的行**跳过**(空值不动 —— 那可能是英文导出,仍走原有兜底)。

### 修复后的核对(逐项对上账单自报的数字)

| 项 | 解析结果 | 账单自报 |
| --- | --- | --- |
| 总条数 | 352 = 445 − 93 中性 | 445 笔 |
| 收入 | **29402.99** | 29402.99 ✓ |
| 支出 | 11322.08 + 还款 3200.00 = **14522.08** | 14522.08 ✓ |
| 笔数 | 271 + 4 = **275** | 275 ✓ |

(还款单独成一类是本 App 的设计,加回来正好与账单一致。)

### 验证

- 真实文件跑通:修复前 **0 条** → 修复后 **445 条**,第一笔日期、金额、备注都对
- 新增 4 条测试:Excel 序列号还原(含账单里的真实序列号)、非法值返回 null、
  中性交易跳过(用一小段 CSV 走真实解析器)
- **证伪**:去掉中性交易跳过 → 该用例立刻失败(3 条而不是 2 条)
- 前端 1194 项 / 160 文件、服务端全过、九道闸门 + 演示库基线全 0

### 顺带说明

这份账单里 **93 笔中性交易不会被导入**。如果你希望它们也进账本(例如当作"转账"记),
那需要账本先有"转账"这个概念 —— 现在没有,所以先跳过并在汇总里计入"跳过条数"。
