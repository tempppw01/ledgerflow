## 重复点「生成支出」,人会被丢进已有那笔交易的编辑页

这一版 1 个提交。换到**订阅管理**这条线上继续找同类问题。

### 先说保护是对的

store 里有一套重复保护:同一天、同一账户、同一金额、备注含订阅名,就**只记一次**,
并返回**已有那笔**的 `transactionId`,同时带上 `duplicated: true`。
我在 store 层先验证了它确实成立:

```
第 1 次生成 → { transactionId: 'v27pigk8', duplicated: false }  交易数 1,续费日 11-13 → 12-13
第 2 次生成 → { transactionId: 'v27pigk8', duplicated: true  }  交易数 1,续费日 12-13(没有再推进)
```

### 问题在页面

`handleGenerateTransaction` **完全不看** `duplicated`,拿到 id 就
`navigate('/transactions/<id>')` —— 而那是交易的**编辑页**。

于是「双击生成支出」的实际体验是:

- 没有新记录(对的)
- 也没有任何提示(错)
- 人却落在一个**已有支出**的编辑表单里 —— 顺手一改就把那笔已经记好的支出改了

### 改法

- `duplicated` 分支:留在订阅页,给一条页面级说明
  「今天已经为「Spotify Premium」生成过支出,没有重复记账。」
- 说明放在**页面级**位置,不塞进表单里的 error 行 —— 那个表单默认是收起的,
  塞进去等于没说
- 正常生成时清空说明,照旧跳转到新交易的编辑页

  页面出现上面那条说明(截图确认位置与样式)
- 新增 **2 条**回归测试(重复时提示且不跳走;正常生成不出提示),

### 仍然记录在案、没有动的

- 删除「生成出来的那笔」时,订阅上的 `last_generated_at` 不会回退 —— 它只是
  「上次生成时间」的标签,不影响余额与统计,暂不动
- 重复判定依赖备注里含订阅名;用户若手工改掉那笔交易的备注或金额,
  再生成时会被当成新的一笔。这是判定规则本身的边界,不是这一版要改的
