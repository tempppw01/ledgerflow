## 修:触摸端和"系统偏好"这一层,之前基本没管

上一批发的是"界面到底有没有按设计渲染出来"。这一批往下一层:前端的规范文档(Apple 的
流体界面/可访问性那套、WCAG 的判据)里明确要求、而这个项目**一处都没响应**的地方。

三条用户能直接踩到,先说这三条。每一条都有浏览器实测数据,没有一条是"读代码觉得不对"改的。

### 最要紧的三条

| 问题 | 后果 |
| --- | --- |
| 触摸端**:hover 规则 307 条,`@media (hover: hover)` 守卫 0 条** | 点过的控件**一直亮着**,直到点了别处 —— 看起来像"一直是热的" |
| 系统开了「减少透明度」时,7 处毛玻璃完全没反应 | 背后的内容被糊成一片,文字压在上面更难读 |

### 一、触摸端「悬停粘住」:307 条 :hover 补上守卫

触摸设备没有真正的悬停能力,但浏览器会把**一次点按当成 hover,而且松手后不撤销**。
390 触摸视口实测:

| 元素 | 点按前 | 点按后(并一直保持) |
| --- | --- | --- |
| `.mobile-nav-toggle` | `background: transparent` | `oklab(0.768595 … / 0.083)` |
| `.topbar-account-trigger` | `transparent`、`transform: none` | `rgba(232,237,245,.73)`、`translateY(-1px)` |
| `.language-switcher-trigger` | 常态 | 底色 + 阴影 + 边框 + 字色**四处**同时变 |

改法是把 `:hover` 声明原地包进 `@media (hover: hover)`。关键在于**媒体查询不改变优先级、
也不改变源顺序**,所以对桌面鼠标的生效声明完全相同 —— 是给已有规则补条件,不是重设计。

- 222 条整条都是 hover → 整条包起来
- 83 条混了 `:focus-visible` / `.is-open` → 拆开,hover 进守卫,其余留在外面,焦点态不能被一起关掉
- 2 条 `:not(:hover)` / `:has(:hover)` 语义是"不处于悬停" → 保持原样

改写全程走 postcss 节点偏移、只动必要字符(这些文件不是 prettier-clean 的,跑格式化会带出
大量无关 diff),落盘前逐文件比对"有悬停能力的设备"看到的(选择器, 声明)集合,完全一致才写入。

**这不是 `:active` 缺失** —— `button:active:not(:disabled)` 早就全局有了,按下的瞬时反馈是有的;
缺的只是"触摸端不该套用悬停态"。

复测(审计新增致败项 `touchHoverReactive`):

| 档位 | 改前 | 改后 |
| --- | --- | --- |
| 桌面 1440(悬停**应当**生效) | 24 / 23 / 24 / 23 | 24 / 23 / 24 / 23,**落定值逐字节相同** |
| 触摸 390(悬停**不该**生效) | 10 / 12 / 16 / 18 | **0 / 0 / 0 / 0** |

反向验证:只去掉 `global.css` 的守卫,审计立刻从 46 个组合 0 问题变成 **46/46 全部致败**(`exit=1`)。

### 二、7 处毛玻璃响应「减少透明度」

`prefers-reduced-transparency: reduce` 此前**一处都没管**(全站只处理过 `prefers-reduced-motion`)。
按用途分两类,没有一刀切:

| 类别 | 选择器 | 改法 |
| --- | --- | --- |
| 常驻框架 | `.sidebar`、`.workspace-topbar`、`.chat-input-bar`、`.chat-topbar`、`.investments-support-sticky-title` | 去掉模糊 + 换不透明底色 |
| 遮罩层 | `.settings-overlay`、`.transaction-filter-dialog-backdrop` | **只去模糊,保留压暗** |

遮罩层为什么不一并做实心:它本来就该"压暗背后的内容",换成不透明会把上下文全遮掉,比模糊更糟。

途中踩到一个可复现的坑:第一版把两个顶栏的覆盖写进了共用块,**实测没生效** ——
同为单类选择器(0,1,0),而它们的原始规则在文件第 776 / 4499 行,排在共用块后面,
同优先级下后写的赢。改成每个覆盖紧跟自己的规则后才通过(`blur(10px) → blur(10px)`,已确认)。

亮色 + 暗色各验一遍,7/7 通过。因为全部包在媒体查询里,默认渲染**按构造完全没变**。

### 三、2.5.8 的判据换对了,顺手补了一个 0.3px

原来的"触控目标太小"检查用的是 44px(AAA/平台指南线),63 个组合报出 1989 条,
真正不达标的看不见。现在按 WCAG 2.5.8(AA)的 24×24 判据来,并实现它自己列的四条豁免
(间距、行内、用户代理、必要),噪声降到只报真问题;44px 那档改成"只在触屏档位、只报告"。

换完判据立刻抓到一个:`收起欢迎横幅` 量出来 **23.7031×44px**,差 0.3px。
补 `min-width: 24px` 后达标。反向验证:去掉这条 `min-width`,审计精确报出这 2 项。

### 四、一处"看着像漏改,其实是刻意"的记录

审计里 `tinyText`(字号 < 11px)一共 19 类元素 / 496 处,全部落在图表刻度、热力日历、
徽标这类密集微标签场景。按 2× 设备像素逐个截图目视过:实际密度下读得出,抬到 12px
反而会顶掉格子里的金额或让横轴月份互相压字。WCAG 不规定最小字号,所以**不改**,
把判断和证据写进 `docs/verified-invariants.md`,免得下次又被当成漏改。

### 顺带确认**不是**问题的两件事

- **强制配色(Windows 高对比度)**:8 条路由实测 0 个元素消失。强制配色会把渐变/阴影
  全部去掉,但浏览器同时把底色强制成 `Canvas`(实测有底色元素 95 → 599、70 → 389),
  所以没有"只靠渐变表现自己"的元素被弄丢。
- **暗色主题对比度**:`audit:contrast` 本来就把浅色/深色两套主题都跑了,并校验
  `data-theme` 实际生效,不是漏项。
