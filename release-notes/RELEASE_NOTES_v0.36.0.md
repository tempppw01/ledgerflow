## 修正订阅续费日期在负时区下跳月(UTC-5 会把 1月31日 推到 3月1日)

### 问题

`advanceSubscriptionDate` / `addMonthsClamped` 用 **UTC 解析 + 本地 getter** 混着算日历:

- `new Date('2026-01-31')` 按 UTC 零点解析;
- 在 UTC-5 上那是「1月30日 19:00」,`getDate()` 得到 **30**;
- 于是「日」按 30 夹到 2 月 28 日,再被时区换算推回 `2026-03-01T00:00Z`。

结果:**整段二月被跳过**。实测:

| 输入(月付) | UTC+8 结果 | UTC-5 结果(错) |
| --- | --- | --- |
| `2026-01-31` | 2026-02-28 | **2026-03-01** |
| `2026-03-31` | 2026-04-30 | **2026-05-01** |
| `2026-11-13` | 2026-12-13 | 2026-12-13 ✓ |

也就是说,**UTC 以西的用户**只要续费日落在 29/30/31 号,点一次「生成支出」就会把续费日
推到下下个月的 1 号,首页「下一笔续费」跟着错一个月。

### 修复

日历运算全部改用 **UTC 组件**(`getUTCDate` / `Date.UTC` / `setUTCDate`),结果与运行环境
时区无关;输出格式跟随输入:**纯日期进、纯日期出**(`<input type="date">` 与账本里存的都是
这种,之前会被转成完整 ISO,现在保持原格式),带时间的 ISO 进、ISO 出。

空值、非法日期、自定义周期缺天数的行为不变 —— 一律原样返回,不抛错。

### 测试

`subscriptionSchedule.test.ts` 重写为 **17 项**,新增的网格不变量覆盖 2024–2028 全部月份 ×
日期(1/15/28/29/30/31)× 4 种周期:

- 输出格式固定 `YYYY-MM-DD`
- 严格向前推进,绝不原地或倒退
- 月份恰好前进一档(1/3/6/12),日期按目标月天数夹住
- 自定义周期推进的天数恰好等于参数(7/30/90/365)
- 连续推 12 次不漂移,年份恰好 +1

**时区无关性实测**:同一套测试在 `UTC` / `Asia/Shanghai` / `America/New_York` /
`Pacific/Kiritimati`(UTC+14)/ `Pacific/Midway`(UTC-11)下全部 17 项通过。

**反向验证**:把实现临时还原成旧的「本地 getter」版本,在 `TZ=America/New_York` 下立刻红
(`expected 2 to be 1`、`expected '2027-05-12T23:00:00.000Z' to be '2027-05-13T00:00:00.000Z'`),
证明这些断言真的能抓住这个 bug,而不是恒真。
