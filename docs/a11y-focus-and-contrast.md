# 焦点、对比度与页面结构(a11y 现状与复测方法)

这份文档记录容易被忽略、但直接影响「能不能用」的几件事:**键盘焦点看不看得见**、
**文字/图标够不够清楚**、**页面结构机器读不读得懂**。每处都附了复测方法,改动后可以重新量一遍。

## 1. 焦点可见性

### 问题

除了少数组件自定义了 `:focus-visible`,**绝大多数可聚焦元素回退到浏览器默认的
`outline: auto` 1px 深色描边** —— 在深色主题上对比度只有 1.0–1.3:1,键盘用户看不出焦点在哪。
实测(按 Tab 逐个检查 22 个焦点位置):

| 路由 | 仍用浏览器默认焦点环(改前) |
| --- | --- |
| 交易流水 | 18 / 22 |
| 首页 | 16 / 22 |
| 还款管理 | 17 / 22 |

### 改法

`global.css` 的 Reset 区加一条全局规则:

```css
:focus-visible {
  outline: 2px solid var(--color-primary);
  outline-offset: 2px;
}
```

组件自带的 `.x:focus-visible`(选择器更具体)仍然优先,不会破坏既有设计。
改后上面三条路由的「浏览器默认焦点环」计数全部为 **0**,焦点环是 2px 琥珀色、
带 2px 偏移,在深色底上约 8:1。

### 复测

用键盘 Tab 走一遍,读 `getComputedStyle(document.activeElement).outlineStyle/outlineWidth`;
`outlineStyle === 'auto'` 就说明还在吃浏览器默认样式。

## 2. 对比度(含一处品牌决策)

### 已修:主按钮

所有主按钮原本是「白字 + 琥珀底」。按 WCAG 公式计算,白色在 `#f59e0b` 上只有 **2.15:1**,
AA 要求 4.5:1。其它强调色同样不合格。

改法:新增 token `--color-on-primary`,按每个强调色算最优组合:

| 强调色 | 主色 | 文字色 | 对比度 |
| --- | --- | --- | --- |
| amber | `#f59e0b` | `#1c1917` | 8.14 |
| emerald | `#10b981` | `#1c1917` | 6.89 |
| rose | `#f43f5e` | `#1c1917` | 4.76 |
| violet | `#7c3aed`(压深一档) | `#ffffff` | 5.70 |

violet `#8b5cf6` 白字 4.23 / 黑字 4.13,两头都不合格,所以压深主色一档。

**这是一处肉眼可见的品牌改动**(主按钮由白字变近黑字)。回滚方式:把各强调色块里的
`--color-on-primary` 改回 `#ffffff`,对比度会退回不合格。

### 复测方法与已知误差

逐元素算 `color` 与最近不透明祖先背景的 WCAG 对比度。两个**测量陷阱**:

1. SVG 的 `fill` 不是 `color`,直接读 `color` 会得到假失败(首页趋势图标签曾因此误报)。
2. 给元素自身背景做判断时,若元素是「琥珀底 + 琥珀焦点环」,`outline-offset` 让焦点环画在
   父级背景上 —— 数值上看起来是 1.04:1,实际是琥珀环落在深色底上,肉眼很清楚。

首页目前仍报 4 条,经截图核对是第 2 类误差,不是真问题。

## 4. 页面结构:跳转链接、文档标题、标题层级(2026-11 修好)

这三条都是 Level A / AA 的硬要求,而且都不能靠「看起来对」判断,只能实测。

### 4.1 跳转链接(WCAG 2.4.1,Level A)

侧边导航有几十个链接,键盘/读屏用户每换一页都得 Tab 穿过整条导航才能到正文。
`AppLayout` 首位现在有一个 `.skip-to-content`,目标是 `<main id="main-content" tabIndex={-1}>`。

两个容易做错的地方:

- **只加 `id` 不够**。焦点不会跟着锚点跑,回车后 Tab 仍然从导航继续走,所以要
  `tabIndex={-1}`(不进入 Tab 序列,但可由脚本/锚点聚焦)。
- **必须真的可见**。清单明确写「聚焦时必须可见」,所以 `.skip-to-content` 平时
  1×1 裁切,`:focus` 时恢复成正常尺寸。写成 `display:none` 或永远 `opacity:0`
  等于没有 —— 屏幕阅读器拿得到,键盘用户看不到。

实测:22 条路由 22/22 存在;未聚焦时 1×1,聚焦后 102×42、背景 `#f59e0b`。

### 4.2 文档标题(WCAG 2.4.2,Level A)

此前**所有路由共用一个 `document.title`**(只在 i18n 初始化时写一次),浏览器标签页、
历史记录、书签里完全分不出页面。

现在唯一写入方是 `src/shared/lib/documentTitle.ts` 的 `useDocumentTitle(pathname)`,
它是一张「路由 → 标题 key」的表 + 兜底。i18n 里原来的 `applyDocumentTitle` 已删除:
留着就是第二个写入方,切语言时两边会打架。

踩过的坑:`/transactions` 与 `/transactions/new` 前缀重叠,最早那版把尾斜杠归一化后
`/transactions` 命中了「编辑流水」。现在用显式 `exactKey` / `exactFallback` 区分,
并有单测钉住(`documentTitle.test.ts`,9 条)。

实测:22 条路由标题两两不同,且随语言切换跟随。

### 4.3 标题层级(WCAG 2.4.6,AA)

**根因是两个「条件性 h1」**:侧栏品牌名写成 `<h1>` 但只在侧栏折叠时渲染,而真正的
页面标题(`currentWorkspaceTitle`)渲染成了 `<div>`。结果侧栏展开时全站 `h1` 数量为 0,
折叠时又变成两个。

现在的约定是**顶栏标题就是页面唯一的 `<h1>`**,正文各区块从 `h2` 起:

- `AppLayout`:顶栏标题改成 `<h1>`;品牌名改成 `<span class="topbar-brand-name">`
  (品牌名不是标题)。样式在 `global.css` 用 `.workspace-topbar .workspace-topbar-title h1`
  拉回继承值 —— 不这么做会被原来那条给品牌名写的 17px 规则顶掉,顶栏标题会突然变大。
- 8 个页面(账户与分类 / 智能预算 / 投资理财 / 帮助 / 关于 / 数据与备份 / 还款管理 /
  工资工具)正文里原来也渲染 `<h1>`,与顶栏同名,现在降为 `<h2>`。
  **降级必须同步改 CSS**:这些页面的样式是 `.xxx-header h2` 这种「类名 + 标签」复合
  选择器,只改 JSX 会丢样式。
- 除首页外还有 3 处跳级:订阅概览的统计标题 `h4`→`h3`、智能预算分类卡 `h4`→`h3`、
  AI 助手「请先配置 API 密钥」`h3`→`h2`。

同一轮还发现 **404 页在 `AppLayout` 的 `<main>` 里又套了一个 `<main>`**(HTML 规范不允许
嵌套,地标重复):`RouteErrorView` 加了 `insideLayout`,站内 404 用 `<div>` + `<h2>`,
根级错误边界(整页接管、没有外层布局)仍是 `<main>` + `<h1>`。

### 4.4 怎么复测

`scripts/audit-ui-browser.mjs` 已把这些做成断言(`h1Count`、`headingSkip`、`skipLink`、
`mainLandmark`、`duplicateIds`、`missingAlt`、`buttonsWithoutType`、`positiveTabindex`、
`autofocus`),任一不合就致败。注意 `mainLandmark !== 1` 同时能抓到「没有 main」和
「嵌套 main」两种。

本机跑不起来时(Playwright 浏览器版本不匹配,见 `docs/HANDOVER.md`)用 MCP 浏览器按
同样口径量:逐路由读 `document.querySelectorAll('main').length`、可见标题序列、
`h1` 数量、`a[href="#main-content"]`。

当前结果:**21 条路由全部通过** —— 每条 1 个 `h1`、无跳级、恰好 1 个 `main` 且不嵌套、
有跳转链接、`#main-content` 存在、无重复 id、文档标题唯一。

## 5. 交易表格:整行详情必须能用键盘打开(WCAG 2.1.1,Level A)

### 问题

交易列表的行是「点开详情」的唯一入口,但它是 `tabIndex={-1}`,行内又没有按钮或链接。
实测:8 行交易、行内 0 个按钮,连按 40 次 Tab 都碰不到任何一行。也就是说
**纯键盘用户根本打不开交易详情**。移动端不受影响,那一侧每项都有「更多操作」按钮。

### 改法

没有把每行都设成 `tabIndex={0}` —— 几十行全进 Tab 链会让键盘用户寸步难行。
改成 **roving tabindex**:整张表只占一个 Tab 停靠点(默认第一行),`↓`/`↑` 在行之间移动,
`Enter`/空格 打开详情。

实现要点:`tabIndex` 由 `(rovingRowId ?? rows[0]?.item.id) === item.id ? 0 : -1` 决定,
`onFocus` 记住当前位置,`onKeyDown` 里用 `parentElement.querySelectorAll` 找同表行并按偏移
聚焦。注意 `rows[0]` 是行视图对象,交易 id 在 `rows[0].item.id` 上(写成 `rows[0].id`
过不了类型检查)。

### 复测

`TransactionTable.test.tsx` 末尾两条测试钉住:只有一行是 `tabindex=0`、`↓` 会换行并跟随、
`Enter` 与空格都会带着正确 id 调用 `onOpenDetail`。

**这两条做过破坏性验证**:把 `tabIndex` 改回 `-1`,第一条立刻失败
(`expected '-1' to be '0'`),恢复后全过 —— 不是那种「怎么写都绿」的测试。

## 6. 拖拽类操作必须有非拖拽入口(WCAG 2.5.7 AA / 2.1.1 A)

> **先厘清条款归属,这里我自己一开始就写混过。**
> 两个条款要求的东西不一样,不能用一件事去满足两件事:
>
> | 条款 | 要求 | 谁能满足它 |
> | --- | --- | --- |
> | **2.1.1 键盘(A)** | 功能要能用键盘操作 | 方向键、按钮、任何键盘可达的入口 |
> | **2.5.7 拖拽移动(AA)** | 功能要能用**不拖拽的单指操作**完成 | 点击类控件:按钮、预设档位、点击选中 |
>
> **键盘入口满足 2.1.1,不满足 2.5.7** —— 因为 2.5.7 明确要求的是「single pointer」,
> 也就是一根手指/一个指针的**点击**,不是按键。
> 所以下面这些"补了方向键"的改动,准确的功劳是 2.1.1;要完全满足 2.5.7,
> 还得给每个尺寸调节控件配一个**点击就能做到**的入口(预设档位或 ± 按钮)。
> 这部分见本节末尾「2.5.7 还缺什么」。

### 侧栏宽度

侧栏宽度原来只能拖,键盘和只用单指的人改不了。按 **ARIA Window Splitter** 模式补了等价入口:

- 手柄 `role="separator"` + `aria-orientation="vertical"` + `aria-valuenow/min/max`;
- `tabIndex={0}`,←/→ 调宽(16px,按住 Shift 48px),Home/End 到最窄/最宽;
- 拖拽照旧可用,这只是多了一条不依赖拖拽的路。

实测:260 → 276 → 292,End→420,Home→220,侧栏实际宽度同步,焦点环 2px 可见。

### 交易页分栏 —— 顺带查出一个既存 bug

分栏分隔条本来就有 `role="separator"` 和 `aria-label`,但**没有 `tabIndex`、没有键盘处理、
没有 `aria-value*`** —— 等于「告诉读屏这是个分隔条,却动不了」。补的方式同上。

补的过程中发现更严重的问题:**这个分隔条在常见窗口宽度下连拖拽都是失效的**。
根因是判定「要不要上下堆叠」用了两把不同的尺子:

- CSS 按**视口**宽度切:`@media (max-width: 1100px)` 里改成单列并把分隔条 `display:none`;
- JS 按**容器**宽度算:`total <= 1100`。

视口 1440 时容器正好 1084,于是 CSS 照常显示分隔条和 `col-resize` 光标,
JS 却认为「已堆叠」把调整逻辑整个关掉。实测:拖之前 `mainW` 720,拖完还是 720。

修法是两边统一按视口媒体查询判断,容器宽度只用来算宽度上限(`total - 320`),
并额外监听媒体查询变化(容器没变、只有视口跨过 1100 时 `ResizeObserver` 不一定触发)。

实测三种情况:宽视口拖拽 860→817(修复前纹丝不动)、键盘 ←/→/Home 生效、
窄视口 900 时分隔条 `display:none` 且恢复宽视口后上限重算为 764。

### 还没做的

三处拖拽入口现在**都有键盘入口了**(详情抽屉、汇率分栏、AI 浮窗,2026-11-25)。
剩下的是 2.5.7 那一层 —— 见本节末尾。

### 详情抽屉 / 汇率分栏:补上键盘入口

这两处比侧栏和分栏更彻底 —— 它们连 Tab 都到不了:

- **详情抽屉**的手柄是 `<button>`,能 Tab 到,但只有 `onPointerDown` —— 按 Enter/Space
  什么都不会发生。**"能被聚焦"不等于"功能可达"**,这正是 2.1.1 最容易糊过去的地方。
- **汇率分栏**的分隔条是个裸 `<div role="separator">`,没有 `tabIndex`,键盘完全够不到。

改法(与侧栏、表格列宽同一套 Window Splitter 模式):

| | 抽屉高度 | 汇率分栏宽度 |
| --- | --- | --- |
| 方向键 | ↑ 增 / ↓ 减(手柄在顶部,与拖拽方向一致) | ← / → |
| Shift + 方向键 | 48px | 48px |
| 普通方向键 | 16px | 16px |
| Home / End | 最矮 / 最高 | 最窄 / 最宽 |

两处细节值得记下来:

- **手柄改用 `role="separator"` 而不是 `button`**,因为 `aria-valuenow` 只对 range 类角色有效 ——
  挂在 `button` 上无障碍树会直接忽略。CSS 本来就把这个按钮的边框和背景清空了,
  换成 `<div>` 视觉零变化(已比对)。
- **上限必须和拖拽用同一份计算**。汇率分栏原来只在 `mousemove` 里现算 `maxLeft`,
  键盘和 `aria-valuemax` 拿不到 → 抽出 `maxLeftWidth` 供三处共用;
  抽屉同理抽出 `getDrawerHeightBounds()`。表格列宽那里已经踩过"报 656 而实际 640"的假读数。
- **上报值要落在 `[min, max]` 里**。抽屉打开时的高度由 CSS 决定,量不到(元素没布局)就会报 0,
  而 `aria-valuemin` 是 300 多 —— 读屏用户会听到"最小值 378、当前值 0"这种自相矛盾的话。
  所以在打开时量一次真实高度,并把上报值钳进区间。
- 汇率分隔条原来只有 `:hover` 高亮,现在可聚焦了必须补 `:focus-visible`(2.4.7 / 2.4.11)。

**复测(浏览器,逐步取证)**:

- 汇率:420 → 436 → 452 → 468 → `End` 664 → `Home` 320,
  `--exchange-left-width` 每一步都跟随。
- 抽屉:`ArrowUp` 后 `aria-valuenow` 536、面板实测 536px;552 → 552px;`End` 876;`Home` 378。
  **报值和真实高度逐步一致**,没有假读数。

测试:`TransactionDetailDrawer.test.tsx` 与新增的 `ExchangePage.test.tsx` 各 2 条
(结构 + 按键序列),**都证伪过** —— 把 `onKeyDown` 摘掉,两条按键测试立刻翻红
(抽屉"期望 323 实得 744"、汇率"期望 420 实得 436")。

### AI 浮窗:两条边各自成一个 separator

`InvestmentChatPanel` 的浮窗有 8 个调节手柄(上下左右 + 四角),外面套着一层
`aria-hidden="true"` —— 它挡不住鼠标,却会把里面**可聚焦**的东西从无障碍树里摘掉。
这是 "aria-hidden 里有可聚焦元素" 那类问题的典型来源。

改法:

- **去掉外层 `aria-hidden`**。不参与键盘的 6 个手柄是空的 `<span>`,本来就不会被读出来;
  参与键盘的两条边需要被读出来。
- 只让**右边缘(宽度)**和**下边缘(高度)**可聚焦。**一角同时改宽高在 ARIA 里没有对应的
  单轴语义** —— `separator` 只有一个值、一个方向。与其给角编一个勉强的语义,
  不如让两条边各自成一个诚实的 separator。
- 上限公式与拖拽共用(`getFloatingAxisMax`),并补 `:focus-visible` —— 这两条边平时是
  **完全透明**的命中区,不给焦点样式等于没有键盘入口(2.4.7 / 2.4.11)。

**这里量出一个真的 bug,值得单独记**:

第一版把"基准值"取自已存下来的测量。实测面板真实尺寸是 430×560 @(986, 316),
而打开瞬间量到的是 **413×538 @(995, 339)** —— 面板有入场过渡,量早了,而且之后再也不重量。
两个后果:

- 按一下 `→`,面板从真实的 430 **先缩到** 429(基准是陈旧的 413);
- `aria-valuemax` 因为用了陈旧的 `left`,报 429 而真实上限是 438,凭空少了 9px。

修法两条并用:**按键时一律以实时矩形为基准**(不看状态里的测量值),
并在**聚焦手柄时重量一次**刷新 `aria` 上报的值。

复测(浏览器,逐步取证):聚焦宽度边时 `aria-valuenow` = 430 = 面板实测宽,
`aria-valuemax` = 438 = 1440−986−16;按 `→` → 438 且面板实测 438;
高度边 560 → `↓` 568(实测 568)→ `Home` 360(实测 360)。
**报值和真实几何逐步一致**,不再有假读数。

测试:`InvestmentsPage.ai.test.tsx` 新增 1 条。这里的桩有个讲究:jsdom 的
`getBoundingClientRect` 恒为 0,所以桩一个**跟随内联样式**的矩形(组件把
left/top/width/height 写成内联样式,读回来就等价于布局跟随变化)。
**用固定值桩是不行的** —— 每按一下读到的都是同一个基准,反而测不出真实行为。
**证伪过**:把宽度分支关掉,"期望 500 实得 516" 立刻翻红。

⚠ **2.5.7 仍未满足的两处**:方向键解决的是 2.1.1,而 2.5.7 要的是**单指、非拖拽**的入口。
点击分隔条/手柄本身仍然什么都不做。**列序与列宽已经补上按钮**(设置面板里的 ↑/↓ 与
收窄/加宽),剩下**侧栏宽度、交易页分栏、表格列宽以外的几处分隔条**还没有点击式入口
(预设档位或 −/+ 按钮)。UI/UX 规范库在这里给的是同一句处方:
「Add buttons menus or tap-to-move controls」/「Move up and Move down buttons beside drag handle」。

### 列序:设置面板里加「上移 / 下移」

列序原来只能在表头拖。现在「筛选设置 → 表格显示」里每一项右侧有一对 ↑/↓ 按钮:

- 走的是**同一条** `handleColumnReorder`,两条路径改同一处状态,不会出现两边不一致;
- 首项禁用「上移」、末项禁用「下移」,避免点出无变化的动作;
- `aria-label` 是「上移 账户」这种带列名的形式,读屏不会听到一屏"上移 上移 上移";
- 按钮 **24×24**(WCAG 2.5.8 目标尺寸最小值 AA 的底线,一开始写成 22px 是不合规的),
  相邻按钮中心距 26px,24px 圆互不重叠。

实现上有个坑:`columnOptions` 是静态列表、不带顺序,所以要把 `columnOrder` 一起传进筛选组件,
再按它排一遍;`columnOrder` 里缺的 key 要补在后面,否则以后新增列会在设置里"消失"。

`TransactionFilters.test.tsx` 两条测试钉住:上移/下移各自传给 `onColumnReorder` 的目标 key 正确、
首尾按钮禁用。做过破坏性验证 —— 把「上移」的目标改成自身,测试立刻报
`expected spy to be called with ['type','date']`。

### 表格列宽:顺手查出「宽度根本不生效」

补列宽键盘入口时发现,这个功能此前**整体是坏的** —— 手柄能拖、状态也在变、
`<colgroup><col style="width">` 的内联宽度确实写进了 DOM,但**表格从不响应**。

隔离测试定性(Chromium):

| 做法 | 结果 |
| --- | --- |
| `<col style="width:400px">` | th 仍是 90,表格宽度 887 不变 |
| `th.style.minWidth = '400px'` | th 立刻变 400 |

根因是表格用了 `width: max-content` / `min-width: max-content`,这种尺寸计算下 `<col>` 的
指定宽度被忽略。现在把宽度同时写到表头 `<th>` 的 `width` 与 `minWidth` 上(同一列的 `td`
会自动跟随),列宽才真正生效。

同时把两处「量宽度」的目标从 `parentElement` 改成 `closest('th')`。原来的 `parentElement`
其实是排序 `<button>`,量到的是按钮宽度而不是列宽。

**一个测量教训**:我第一次测「拖拽」时用 Playwright 在 1px 宽手柄的中心按下并水平移动,
结论是「拖拽无效」。换成直接给手柄派发 `mousedown` 再给 window 派发 `mousemove` 后,
列宽 90 → 150 —— 拖拽其实是好的,是我的合成点击没打中目标。
**「按下去没反应」和「没按到」在自动化里长得一模一样**,所以这类结论必须用另一种方式复验。

另外键盘上限必须与 `TransactionsPage` 的 `COLUMN_MAX_WIDTH` 一致(都是 640)。
不一致时会出现 `aria-valuenow` 报 656、实际列宽停在 640 的假读数。

`TransactionTable.test.tsx` 两条测试钉住:宽度必须落在 `th` 上(去掉就失败)、
手柄可聚焦且 Home/End 分别回调最窄/最宽。

### 2.5.7 还缺什么(截至 2026-11-25)

按「点击类入口」这一条严格核对,现状是:

| 控件 | 2.1.1 键盘 | 2.5.7 单指点击 | 说明 |
| --- | --- | --- | --- |
| 列序(表头拖拽) | ✅ | ✅ 已满足 | 设置面板里的 ↑/↓ 是**按钮**,点一下就能改序 |
| 侧栏宽度 | ✅ | ❌ 仍缺 | 只有方向键;折叠按钮改的是"折/展",不是宽度 |
| 交易页分栏宽度 | ✅ | ❌ 仍缺 | 同上 |
| 表格列宽 | ✅ | ✅ 已满足 | 设置面板里每列一对「收窄 / 加宽」按钮,点一下就能改 |
| 详情抽屉拉伸 | ✅ 已补 | ❌ 仍缺 | 原来连 Tab 都到不了;现可聚焦 + 方向键/Home/End |
| 汇率分栏宽度 | ✅ 已补 | ❌ 仍缺 | 同上 |
| AI 浮窗 | ✅ 已补 | ❌ 仍缺 | 8 个手柄原来全在 `aria-hidden` 里;现右/下两条边可聚焦 |

**没有把"键盘"当成 2.5.7 的答案糊过去。** 剩下这几处要真满足 2.5.7,
需要的是**点击就能做到的宽度入口** —— 常见做法是预设档位(窄/标准/宽)或成对的 − / + 按钮。
这是 UI 设计决定,不是顺手能加的:9 列各配一组 ± 会让设置面板变得很挤,
所以先记在这里,想清楚放哪再动,而不是为了消掉表格里的一个 ❌ 硬塞按钮。

## 7. 可访问名必须包含屏幕上那行字(WCAG 2.5.3,Level A)

### 问题

「标签包含可见文字」说的是:按钮上写什么字,读屏/语音控制就该能按那行字找到它。
不满足时,真正受损的是**语音控制用户** —— 他看着屏幕喊「首页」,而可访问名是「第一页」,
点了没反应,而且他完全不知道为什么。

实测 12 条路由,抓出两处真实违规:

- **分页 4 个按钮**:可见 `首页 / 上页 / 下页 / 末页`,而 `aria-label` 是
  `第一页 / 上一页 / 下一页 / 最后一页`。中文四个全不匹配;英文里 `Prev`
  也不在 `Previous page` 里。
- **日期选择器触发按钮**:组件固定用「选择日期」当 `aria-label`,但调用方会把占位符写成
  「筛选日期」「可选」—— 屏幕上的字同样不在名字里。

### 改法

- 分页按钮**去掉 `aria-label`**,让可见文字直接当可访问名(与 GOV.UK 等设计系统的做法一致)。
  可见的 `首页/上页/下页/末页` 本身已经清楚,旁边还有「第 1 / 3 页」的指示。
- 日期选择器在**显示占位符**时把占位符放到名字最前面,得到「筛选日期, 选择日期」。
  注意只在没选日期时这么做:已选日期时屏幕上是「2026-11-08」这类**值**而不是标签,
  2.5.3 不要求把值塞进名字,塞了反而让名字随值变化、更难用语音匹配。
- 触发按钮里显示的文字和用来拼名字的文字现在共用同一个变量,
  否则以后改一处忘另一处,这条又悄悄坏掉。

### 复测

浏览器里对每个有可见文字的控件,比较「可见文字」与「可访问名」是否包含关系。
**注意误报**:图标字形(`▴` `🐞` `⋯`)和 emoji(`🍜 餐饮`)会被算进 `innerText`,
但它们不是标签文字。剔除纯符号后再看,剩下 25 条经复核全部是这类误报
(名字里都含有真实文字)。当前 `/transactions` 上违规数 **0**。

`TransactionTable.test.tsx` 与 `TransactionFilters.test.tsx` 里有对应断言,
其中一条专门用 `toHaveAccessibleName(/筛选日期/)` 钉住 2.5.3。

## 8. 表单控件的边框对比度(WCAG 1.4.11 非文本对比度,AA)

### 问题

1.4.11 要求:**控件的可感知边界**与相邻颜色的对比度至少 3:1。
输入框的边框不是装饰,它就是这个控件"能点、能输入"的全部视觉线索 ——
灰色边框低于 3:1 时,低视力用户看不出这里有个输入框。

实测 17 条路由上所有可见的 `input / select / textarea`,用
`--color-border`(#d9dfeb 一类的浅灰)做边框的一共 **55 个**,对白底的对比度约
**1.2 : 1**,远低于 3:1。

### 改法

- 新增令牌 `--color-border-control`(`tokens.css`):浅色 `#7d8695`、深色 `#656d78`。
  **没有改 `--color-border` 本身** —— 同一个令牌还用在卡片、区块分隔线上,
  把它整体压深会让整个界面变重、变脏。控件边界和装饰分隔线是两种东西,应该两个令牌。
- 新增 `form-controls.css`,用
  `:is(input, select, textarea):not([type='checkbox']):not([type='radio']) { border-color: var(--color-border-control); }`
  统一兜底,并在 `index.css` 里**放在最后**(tokens → global → … → mobile-shell → form-controls)。
- 为什么用 `:is(...)` 加两个 `:not(...)`:选择器权重是 0-2-1。
  最初写成 `select { … }` 这种兜底(权重 0-0-1)时,全部被
  `.balance-change-field select` 之类的页面级规则压掉,55 个只修好 2 个。
  提高权重后才真正生效。
- 复选框/单选框排除在外:它们的可见部分是勾选标记,不是边框。

### 逐处例外(容器提供边界的情况)

有些控件把边框写成 `border: 0`,由外层容器画框。这种情况下**容器的边框**必须达标:

| 位置 | 容器 | 处理 |
| --- | --- | --- |
| `/assistant` 聊天输入框 | `.chat-input-main` | 容器边框改用控件令牌,实测 3.37 ✓ |
| `/repayment-management` 月收入输入 | `.repayment-income-field` | 原用 `var(--color-border)`,实测 **1.23 ✗** → 改用控件令牌 |

第二处就是这样被抓出来的:只扫控件本身会漏掉它(它的 `border-width` 是 0,看起来"没边框"),
必须沿着祖先找最近一个有可见边框的元素再算对比度。

### 暗色主题

暗色下同一套令牌取 `#656d78`。切到暗色后重扫 `/transactions`:
12 个控件,最低 **3.37**,低于 3:1 的 **0 个**。

### 复测方法

对每个可见控件算 `contrast(border-top-color, 最近不透明祖先背景)`:

- `border-width` 为 0 时,向上找最近一个有可见边框的祖先,算**它**的对比度。
- **注意误报**:`color(srgb …)` 形式的颜色用只匹配 `rgba()` 的正则解析会直接漏掉,
  这一步要手工合成颜色再算。
- 隐藏控件(`display:none` / `visibility:hidden` / `offsetParent === null`)要跳过,
  否则会把弹窗里没打开的控件算进来。
## 9. 错误必须关联到出错的字段(表单规范里标 High)

### 问题

UX 规范把「只在顶部报一句错、不指出是哪个字段」列为**高严重度**问题,
要求是「Show a specific error below the input and reference it with aria-describedby」。

实测全仓库只有**一处**做对了:`TransactionEditPage` 的金额输入框
(`aria-invalid` + `aria-describedby="tx-amount-error"`)。其余表单(薪资工具、
还款管理、预算向导、资产负债模拟、登录)都是顶部一句 `role="alert"` ——
**读屏用户逐字段 Tab 过去时听不到任何提示**,只有碰巧经过那句话才知道哪里错了。

### 改法与两个真问题

先在**薪资工具**上把模式做对(4 个输入框、7 条错误文案),过程中撞出两个真问题:

**（1）文案表里的一条键是坏的,英文界面漏出中文。**
`SALARY_ERROR_EN` 有 7 条映射,其中「请先完成上方工资基础输入,才能计算加班工资」
那条的**键**用的是**半角逗号** `U+002C`,而模型返回的是**全角逗号** `U+FF0C` ——
键对不上,`SALARY_ERROR_EN[error] || error` 就退回中文。**7 条里坏 1 条**,
而且肉眼看两个字符串一模一样,只有按码点比才看得出来。

顺带说明这个 bug 是怎么暴露的:改模型时我手抄这行文案,抄成了半角逗号,
**既有测试立刻翻红**(它一直钉着全角)。顺着这条线去核对整张映射表,才发现
坏的是**卡片里的键**而不是我的新代码 —— 也就是说这个中文泄漏在改动之前就存在。

新增的守卫测试**用会触发错误的输入枚举消息**,而不是手抄字符串:

```ts
const messages = [
  getSalaryInputError({ monthlySalary: '', workingDays: '', dailyHours: '' }),
  getSalaryInputError({ monthlySalary: 'abc', workingDays: '21.75', dailyHours: '8' }),
  // ...每条各一个触发它的输入
];
for (const message of messages) {
  const en = localizeCalculatorError(message, 'en');
  expect(en).not.toBe(message);
  expect(/[\u4e00-\u9fff]/.test(en)).toBe(false); // 英文里不许出现汉字
}
```

这样将来改文案或加分支时,漏翻译会被立刻抓住,而不是等用户看到中文才发现。

**（2）判断只写一遍,字段由模型给出。**
模型原来在 `getSalaryInputError` 里直接 `return` 文案。表单还需要知道**是哪几个字段**
错了 —— 两处各写一遍判断迟早走形。改成「**一次求值 → 映射成文案**」:
`evaluateSalaryInput` 返回 `{ kind: 'empty', fields }` 或 `{ kind: 'invalid', field }`,
文案和 `getSalaryInputErrorFields` 都由它派生。既有的 7 条文案测试一条没改、全部通过。

**这一层还要分清"错在谁身上"**:`salaryBase` 那条错误指的是**上方的工资基础输入**,
把加班框标成 `aria-invalid` 是错的。所以额外导出 `getOvertimeInputProblem`,
只有错误确实出在加班字段本身时才标它。

### 复测(浏览器 + 数据库)

清空「月薪」后,只有它被标:

| 字段 | `aria-invalid` | `aria-describedby` |
| --- | --- | --- |
| 月薪 | `true` | `salary-input-error` → 「请先填写月薪、计薪天数和每日工时」 |
| 计薪天数 / 每日工时 | 无 | 无 —— **没被误标** |
| 加班时长 | 无 | 无 —— 错误指的是上方字段,不在它身上 |

测试两层都钉住:`salaryCalculator.test.ts` 钉模型(出错字段、每条错误都有英文),
新增的 `SalaryToolCard.test.tsx` 钉**接线**(属性有没有真的挂到对应输入框上、有没有挂错)。
两条都证伪过:把映射表的逗号改回半角 → 文案测试与英文守卫同时翻红;
把错误关联摘掉 → 组件测试翻红。

⚠ **其余表单还没做**(还款管理、预算向导、登录)。模式已经跑通,照同一套改即可:
模型给出错字段 → 错误的 `<p>` 给 `id` → 字段挂 `aria-invalid` + `aria-describedby`。

### 同一个模式套到第二处:资产负债模拟的预测账单表单

这一处不需要改模型 —— 两条校验分支本来就各自对应一个字段
(`forecastAmountInvalid` → 金额框,`forecastDateInvalid` → 日期框),
只是没有把这个信息传给表单。加一个 `billErrorField` 状态即可。

**关键的一点是"换字段要把上一个清掉"**:金额错一次、再让日期错,
金额框上不能还留着 `aria-invalid`。测试专门断言了这一条
(`expect(amount).not.toHaveAttribute('aria-invalid')`) —— 只测"改对了"不测"改回来",
很容易留下一个一直标红的字段。
