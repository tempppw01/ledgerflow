# 窄屏重排(1.4.10)与 200% 缩放(1.4.4)

> 2026-11-27。补量了此前从未量过的两个 WCAG 条目,并修好一处真实缺陷。
> 配套改动:`src/app/styles/pages.css` 的市场柱状图媒体查询、`scripts/audit-ui-browser.mjs`。

## 1. 为什么这两个条目以前没量过

已有审计只跑 1440(桌面)与 390(移动)两档宽度。但:

- **1.4.10 Reflow 的门槛是 320 CSS px**,不是 390;
- **1.4.4 Resize text 的门槛是 200% 缩放**,此前完全没测。

**390 过不等于 320 过。** 这一轮补充的正是这两档:

| 视口      | 代表什么            | 对应条目 |
| --------- | ------------------- | -------- |
| 320 × 844 | 最窄的 CSS 视口门槛 | 1.4.10   |
| 720 × 450 | 200% 浏览器缩放     | 1.4.4    |

为什么「视口减半」可以代表 200% 缩放:全仓字号 **989 处是 `px`、只有 22 处 `rem`**,
而浏览器缩放(Ctrl +/−)会缩放 px,所以放大 200% 等价于把 CSS 视口减半。

覆盖 21 条路由 × 2 档 = 42 个组合。

## 2. 发现:财务分析页的市场柱状图在 320px 下金额互相压字

- 6 列网格在 320px 下每列只有 **41px**,而 `¥18,563.63` 这类**不可断行**的金额,
  最小宽度是 **61px**;
- 实测**相邻两列金额各重叠 11px(5 对全中)**,最后一列还越出视口 3px,被卡片的
  `overflow` 裁掉;
- 截图里那一行金额糊在一起、读不出来。而 **390px 下完全正常** —— 所以只跑 390
  永远看不见这个问题。

金额本身在 `strong` 里,网格的 `justify-items: center` 也不救:内容比格子宽,
就一定溢出到相邻格上。

### 修法

`@media (max-width: 480px)` 下把网格从 6 列改成 3 列(6/7/8 与 9/10/11 两行),
月份顺序不变。

**480 这个阈值是算出来的,不是试出来的**:6 列要放得下 61px 的金额,每列需要约 68px,
换算成视口就是 `32 + 68 × 6 + 8 × 5 ≈ 480`。低于 480 就不可能不重叠。

### 验证

| 步骤                          | 320px                                | 390px  |
| ----------------------------- | ------------------------------------ | ------ |
| 改前                          | 5 对金额各重叠 11px,最后一列越界 3px | 无重叠 |
| 改后                          | 6 个金额分成 2 行,同行 0 重叠        | 0 重叠 |
| 破坏性(把 `480px` 改回 `1px`) | 又变回 1 行、5 对重叠 11px           | 无重叠 |

第三行是关键:把修复撤销后**必须**重新报错,才说明测量本身有效 ——
否则「改后 0 重叠」也可能只是探针瞎了。

改后同一区域的实测:`grid-template-columns` 三列、每列约 90px,6 个金额全部完整可见。

## 3. 发现:`今日财务看板` 的「净资产构成」在窄屏被压成一列 48px

这条缺陷**在 720px 就已经发生**,不是小屏专属 —— 只是以前没人往那个宽度看。

`.dashboard-net-worth-summary`(卡片右侧「总资产 / 总负债 / 净资产」那三格)base 里自带
`min-width: 210px`;窄屏样式想让它整行落到数值下面,写的是:

```css
grid-column: 1 / -1;
width: 100%;
```

问题在于 `.stat-card` 是 **`display: flex`**。`grid-column` 在 flex 父元素里
**完全不生效**,既不报错也不警告,于是摘要一直挤在数值右边,被压到:

| 视口          | 三列各宽 | 结果                                 |
| ------------- | -------- | ------------------------------------ |
| 1440px(桌面)  | 77.5px   | 正常                                 |
| 720px         | **48px** | 标签与金额都被省略号截掉(`¥20…`)     |
| 439px / 390px | —        | 挤成 2+1 两行,「负债」单独掉到第二行 |

390px 下整张卡高 133px,而隔壁「本月结余」只有 92px —— 一排卡片高度不齐。

### 为什么只加 `flex: 0 0 100%` 第一次没生效

第一版加了 `flex: 0 0 100%`,量出来仍然没换行。原因是**优先级**:

`global.css` 里有一条 `.stat-card > div { flex: 1; min-width: 0 }`,特异性 **(0,1,1)**,
它同时命中摘要这个 `div`,而 `.dashboard-net-worth-summary` 只有 **(0,1,0)** —— 被压住。

更隐蔽的是,这条 `.stat-card > div` 连 base 里的 `min-width: 210px` 也一起清成了 0
(实测 `minWidth = 0px`),只是以前没人量过它。

所以窄屏覆盖必须抬到 `.dashboard-stat-grid .stat-card > .dashboard-net-worth-summary`
(0,3,0),同时给父级加上 `flex-wrap: wrap`。

### 验证

| 视口          | 改前                          | 改后                                                 |
| ------------- | ----------------------------- | ---------------------------------------------------- |
| 720px         | 三列各 48px,金额被截          | 摘要独占整行,三列各 105px,0 截断                     |
| 439px         | 2+1 两行                      | 整行,三列各 122px                                    |
| 390px         | 卡高 133px,与邻卡不齐         | 摘要 y=430 落在数值 y=363 之下,三列各 106px,高度齐平 |
| 360px / 320px | —                             | 三列各 96px / 82.6px,0 截断                          |
| 1440px(桌面)  | 卡片 526×92,摘要 x=585 宽 266 | **完全一致**(桌面未受影响)                           |

顺带删掉 `@media (max-width: 440px)` 里的「3 列改 2 列」:摘要在窄屏已经整行独占,
300px 左右三列每列还有约 92px(标签约 24px + 金额约 64px)放得下,
改 2 列反而必然排成 2+1。

截断检测器做过破坏性验证:强行改成 6 列(每列 49px)后,三项**全部**报「被截」——
说明「0 截断」不是探针看不见,是当时真的没有。

## 4. 1.4.4(200% 缩放)的结果

21 条路由全部通过:0 处溢出、0 处内容被裁,也没有出现文字被容器截断的情况。

## 5. 剩余命中都是「屏幕阅读器专用文字」,不是缺陷

初审时每条路由都报 `skip-to-content` / `visually-hidden` /
`repayment-record-button-label`「文字被裁 1<22」。核对 CSS 后确认三者是同一套技法:

```css
width: 1px;
height: 1px;
overflow: hidden;
clip: rect(0 0 0 0);
```

它是**有意隐藏**给读屏用的(`.skip-to-content` 还在 `:focus` 时恢复可见),
不是内容被裁。所以判定里增加了「高度必须 > 1px」,把 1px 技法排除掉。

## 6. 顺带修好审计脚本自身的三处问题

审计是这套检查的眼睛。眼睛有问题比没有检查更危险 —— 它会给你一份**看起来干净**的报告。

### 6.1 登录会被静默跳过(最危险的一个)

原来的 `login()` 在 `domcontentloaded` 之后立刻用 `count()` 找登录表单。
`domcontentloaded` 早于 React 渲染,而 `count()` 不会自动等待,于是:

`count() = 0` → 整个登录分支被跳过 → 后面每个路由量到的都是**登录页** →
报告照样打印「N 个组合、0 个问题」。

第一次跑出「0 个发现」时就是踩了这个坑:21 条路由的 `main` 文本全是同样的
97 个字符(登录页)。发现方式是把 `main` 文本打出来看,而不是相信计数。

现在:等表单出现 → 填写 → 提交 → 等表单卸载 → **硬断言已经进入应用**;
没进去就直接抛错,**不许把「测量失败」伪装成「没有问题」**。

### 6.2 登录后还有一道数据门

表单卸载后、外壳渲染前,还有「正在载入账本」(`SqlDataSyncGate`)。
那段时间 `nav` 并不存在,拿它当成功信号会误判成登录失败。
所以要等外壳真正渲染出来(`nav` 出现)再断言。

注意不能用「`nav` 可见」当信号:320/390 宽度下侧栏本来就是收起的,
`nav` 存在但 hidden —— 那是正确的响应式行为。

### 6.3 `emptyMain` 永远变不绿

原来只判「`main` 文本 < 60 字符」,于是空回收站(46 字符)与 404 页(55 字符)
**永远报红** —— 这两个都是有正经标题和可点空状态按钮的真页面。
一个永远不会变绿的检查,只会让人学会忽略它。

改为同时看「`main` 里没有标题、也没有任何可操作元素」。

这里有个坑:信号必须**只在 `main` 内部取**。这些页面的 `h1` 在 `main` 之外(布局头部),
如果拿全局 `h1Count` 当条件,把 `main` 清空后仍然 `h1Count=1` → **漏报**。
第一版就是这么写的,被阳性对照抓了出来。

阳性对照两个方向都验过:

| 场景                           | 期望     | 实测 |
| ------------------------------ | -------- | ---- |
| `/recycle-bin` 正常态          | 不报空   | ✓    |
| 404 页正常态                   | 不报空   | ✓    |
| 把 `main` 清空                 | 必须报空 | ✓    |
| 把 `/categories-accounts` 清空 | 必须报空 | ✓    |

### 6.4 让审计能跑起来

本机 playwright 期望 chromium 1255,而 `ms-playwright` 里只装了 1248,
默认路径必然报 `Executable doesn't exist` —— 审计根本跑不起来。
「跑不起来」很容易被当成「没空跑」,所以加了退回已装那一份的逻辑
(也可用 `AUDIT_CHROME_EXE` 显式指定)。

## 7. 怎么重跑

```bash
node server/localSqliteServer.js # 需要 API(LEDGERFLOW_API_PORT 可换端口)
npx vite --port 5333 --strictPort # dev server(Vite 只绑 [::1],用 localhost 访问)
node scripts/audit-ui-browser.mjs --base=http://localhost:5333
```

脚本现在自带 320px 一档(标签 `reflow-320`);`--mobile` 会跑 390 与 320 两个窄宽度,
所以 1.4.10 不会再被漏掉。

最终一次全量结果:**69 个组合(23 路由 × 3 视口)、`problemCount = 0`、退出码 0**。

## 8. 已知的环境噪声(不是页面缺陷)

审计的「控制台错误」检查会把 CDN 图标请求失败算进来:界面图标取自
`pub-….r2.dev/ui/*.svg`。本机直连该域名偶尔要 5.6 秒甚至被重置(走同源 `/cdn`
代理约 2.5 秒),于是偶发 `net::ERR_EMPTY_RESPONSE`。

页面本身渲染正常(`main` 文本 2351 字符、无溢出、a11y 全绿),重跑后该错误消失,
确认是环境抖动。**没有为了让报告好看去削弱这条检查。**
